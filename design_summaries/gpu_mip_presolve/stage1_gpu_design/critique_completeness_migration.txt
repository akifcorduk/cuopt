======== DEFECTS ========
--- 1
design: bulk-first
severity: fatal
where: Section 1 (principle: the device never decides the order of anything), per-part list (start step, make_explicit, dual fixing, parallel-row pair scan, doubleton forest and substitution, storage, record stack all 'Host'), section 6 and milestone M5 (script application only above 2% of hybrid time), section 7
defect: As a plan for 'a complete GPU acceleration' it cannot stand: it moves the tests to the device and leaves on the host every application, the host-owned state (so the state build stays limited by host memory), storage and records. Much of that work is parallel by the design's own description (section 6: for dual fixing, make_explicit, tightening edits, parallel-row merges, alias substitution and zero-cost singleton columns 'the script is known before anything is applied'). The reason given for leaving it is 'the host copy must follow', which is a consequence of this design's choice that the host owns the state, not a measured property of the method. The directive allows the host for small and non-parallel work only.
evidence: Stored node run of the nine instances above 1e7 nonzeros (release_large, 88.3 s): state build 30.21 s, which the design improves by its measured 2.0 to 2.1 times only (at least 14.4 s stay); storage 3.67 s ('None on x86'); doubleton 5.20 s of which only the 11% collection leaves the host; dual fixing 2.36 s with 39,899,589 fixings applied by the host (the test is O(1)); start step 0.19 s. That is at least 25 s of 88.3 s on the host before row rules, singleton columns (dlr2 4.22 s), pair scans, records and any kernel or sync time: a ceiling of 3.5 times, and the design's own projection is 2.0 to 2.4 times. Measurement step, 240 instances: chain length 1 in every call of dual fixing, parallel rows and the doubleton rule; make_explicit makes 2,069,123 bound changes as one loop over columns. For the cascades the prototype of one-algorithm shows that row rules and propagation run as rounds from one state with no instance larger and 234 of 240 hashes equal, so their application 'can be parallelized' in the owner's sense.
fix: None inside the design, because every fix gives up its principle. Keep two pieces as the first stage of another plan: M0 (each visit split into a pure evaluation and an application, the audit, hashes equal to today's) and M1 (device state build with fold kernels). Do not build the mirror of the host's incremental state (M2 journal and slot-identical image) or the replay library (M5): neither is reusable by an engine that applies on the device.

======== MISSING_IN_ALL ========
- A bound on the model-size threshold, so that 'complete' cannot be reached by raising it. All three leave everything below a provisional threshold on the host (1e5 nonzeros in one-algorithm, 2e5 in the other two) and fix it at the last milestone by smallest summed time; device-native says it 'may end near 1e6'. On the 240 benchmark instances 21 lie from 5e4 to 1e5 nonzeros, 29 from 1e5 to 2e5 and 67 from 2e5 to 1e6 (25.2% of today's summed seconds); with a threshold of 1e6, 117 of the 147 instances from 5e4 nonzeros never use the GPU and every acceptance list still passes. Needed: per part a measured crossover (device forced against host, by size class, stored), the threshold derived from it, and the owner's consent to the number.
- A completeness measure in host seconds. Shares in work units say where the work is counted, not where the time goes (certified skips, O(1) visits, host tails). Needed: the profile of a hybrid run by part, with the host seconds outside the driver bounded per size class.
- The strength of the reduced model in the gate against today's engine. All gates compare rows, columns and nonzeros. The batch prototype's own runs show a change those numbers do not see: on neos-1122047 the tightening findings fall from 71,994 to 7,238 and the propagation findings rise from 72,403 to 156,923 with 2 fewer rows; 31 further instances have other propagation finding counts with equal hashes of the reduced model or equal sizes. The owner's main goal is a stronger formulation (A10). Needed: a comparison of bounds and coefficients of the two reduced models on instances whose hash differs, or the root bound in cuOpt for them.
- The cuOpt adapter as it exists (cpp/src/presolve/gprs_presolve.cpp, 398 lines). It takes a host model, copies it into gprs::model_t, and converts the result on the host; adapter mode 3 (A6) then runs four cuOpt reductions through the PaPILO framework on the host model. 'Device arrays in and out' is an open question in all three and planned in none. Also missing: who creates the CUDA context and the memory pool, how the byte budget is set next to cuOpt's early GPU heuristics, which hold about 120 bytes per nonzero during presolve (DESIGN.md section 10) against 40 to 68 for the device state, and how the engine and executor options reach cuOpt's settings for a cluster comparison.
- The hash is computed without condition in presolve() (presolve.cpp, last lines) and so in the adapter too. An option to skip it removes its 5.5% in production with no new function and no replaced stored hash; all three replace the function instead.
- Scope at the edges. Not classified in any design: remove_empty_rows, the comparison of the reduced model with the input for the status 'unchanged' (an O(nonzeros) host loop), the BHW coefficient reduction that A6 calls 'a candidate for the end of Stage 1' and A8 places after the Stage 1c gate, and sparsify with the aggregator (A8 item 2), which come before the wide phases. The plan should say whether these wait for the acceptance and in which form a rule added later must be written.
- The work in review. All three designs and all measurements stand on commit 04692babd; simple probing (edd147a7e) and the parallel-row repair are in review and not accepted (HISTORY). None says in which order the review, the remaining cheap rules and the rewrite are merged, and no node figure exists for simple probing.
- Width and depth on the nine instances above 1e7 nonzeros. No design has it, two put the run late, and the rules for large models (no hand-back, every step on the device) rest on the 30 benchmark instances from 1e6 nonzeros.
- A count of the code. None of the three gives lines per milestone for the host changes, the device code, the tests re-based and the wrong engines re-made (device-native gives one figure for the host).
- None of the three designers read the cuOpt load-balanced kernels they plan to lift; what is liftable rests on the research step's reading.
- GPU time for verification: the device campaign, the second GPU type and Grace Hopper have no estimate of node hours, and a second GPU type has never been run in this project.

======== RANKING ========
Under this lens: 1. one-algorithm, 2. device-native, 3. bulk-first.

one-algorithm first: every part of the scope is classified with an executor, a conflict rule and a statement on today's result; host-only parts are few and named; it has the only measured reductions (two families, 240 instances, nothing lost); one algorithm means one set of rules and checks for both executors; the build without CUDA is the reference. Its defects are all in the way there and have small fixes: keep the order switchable, split G2 and G3 into hash-gated steps (my probes show two of the bundled changes are hash-neutral alone), correct the return threshold, state the host time gate honestly, screen the campaign unions, count the code.

device-native second: equally complete in classification and better in test structure (step equality, a complete presolve at every device milestone, 'no step on seq because its cuda form is missing'), and it keeps an engine switch. It loses on the way there: nothing measured, a second engine with a new state type and about 70 steps in two executors, a composed two-engine presolve as scaffolding, an option redefined in a way that can lose reductions, and the remaining cheap rules and the measurement on the largest instances at the end.

bulk-first third: the safest migration (bit-equal with today at every milestone, all checks and stored results kept) and the cheapest in risk, but it does not meet the directive. Applications, the host-owned state, storage and records stay on the CPU; on the nine large instances at least 25 s of 88.3 s remain host work by construction and its own projection is 2.0 to 2.4 times. Its M0 and M1 belong at the start of the synthesis.

For the synthesis: the algorithm and the acceptance list of one-algorithm; the first two milestones from bulk-first M0 and device-native milestone 0 (evaluation and application split, value-function headers, hashes unchanged); then the canonical state in hash-gated, switchable steps inside today's engine; the device executor with step equality, rule H6 and the hand-back rule of device-native; the remaining cheap rules written once as steps that both orders can run, in the order the owner decides.
