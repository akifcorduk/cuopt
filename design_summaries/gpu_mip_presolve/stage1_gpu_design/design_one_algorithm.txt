======== TITLE ========
Stage 1 on the GPU as one batch algorithm with two executors (host and device) that give the same bits

======== SUMMARY ========
Design from the angle "one algorithm, two executors". Every family of Stage 1 becomes a deterministic batch step: find all candidates on the state as the step found it, resolve conflicts by a fixed rule, apply, recompute the derived data of the touched lines. The step is a pure function of a canonical state (entries of every line in index order, activities always summed from scratch in the lane order of numerics.hpp, work lists as sets served in ascending index, sums of several terms in one fixed order). A host executor (plain C++, sequential) and a device executor (CUDA kernels, CUB sorts and integer reductions) compute the same function bit for bit, so a run with a GPU, a run without one, any GPU type and any threshold give the same reduced model, and the test "device equals host" is kept for every step. Conflicts are resolved without floating-point atomics in three ways: order-free combination (maximum, minimum, integer sums), an ordered fold after a sort (costs, coefficients, side shifts, the objective offset), and integer reservations by smallest index (rows or columns that one reduction needs alone). The hybrid rule sends a step to the device when its work in the engine's own work units is above a constant and keeps small models, short work lists and the last rounds on the host; because both executors give the same bits, no threshold can change a result. The price is that the host engine is rewritten and that today's hashes change once. I measured that price for the two cascade families with the deepest chains by a prototype (row rules and bound propagation as batch rounds, lists in ascending index) in a scratch copy of the engine at commit 04692babd: on the 240 benchmark dumps the status is the same on all 240, the reduced-model hash is the same on 234, no instance has more rows, columns or nonzeros (two have fewer rows: momentum1 65, neos-1122047 2), list rounds rise by 5.7% (row rules) and 0.9% (propagation), rule work units by 2.8% (almost all of it on square41, square47 and neos-1122047), and 45 million random models pass the oracle, the structure check and the crush check without a failure. Engine seconds of the prototype were 12% above today's on a loaded Mac (smallest of 5 runs), which is an upper estimate of the host-path cost. Not measured: the same for the other families, activities summed from scratch, the canonical order, the nine instances above 1e7 nonzeros, and anything on a device. Nothing in the project tree was changed.

1. THE IDEA
(1) A family is not a loop over a list that changes the state as it goes; it is a step: a function that takes the state and returns the next state. (2) The step is written so that its result does not depend on the order in which candidates are computed or applied: candidates are computed on the state as the step found it, conflicts are resolved by a rule that reads indices and values only, and every floating-point sum has one order. (3) The state is canonical: it holds nothing that depends on how it was reached (no accumulated activity, no list order, no slot history). (4) Two executors compute the step: the host executor with sequential loops over the frontier, the device executor with kernels. Because the step is one function with one arithmetic (shared inline functions, compiled for both sides), the two agree in every bit. (5) The driver (host code) runs the same sequence of steps whatever the executor, and chooses the executor of each step by its work.
Why not keep today's order: today's results depend on applying each change before the next test in list order. Reproducing that order on a device is sequential work (the research report: for an arbitrary order the greedy problem is P-complete; PaPILO keeps the order by a sequential apply phase, which limits it to 1.9 times at 32 threads). So either the device is a helper whose results the host replays (the Stage 1b design, overruled by the directive), or the algorithm changes. This design changes the algorithm, once, for both executors.

2. THE CANONICAL STATE (what both executors hold, and what is hashed)
C1 Order of a line. In both orientations the live entries of a line are stored in increasing index of the other dimension at all times. Today this holds at construction only (state.hpp:58-61; move_entry breaks it). With C1 the lane of every entry in the activity fold is a function of the model, the reduced model needs no sort, and a second presolve of the reduced model starts from the same activity bits.
C2 Activities are values, not accumulators. The stored minimum and maximum activity of a row is fold(row) of numerics.hpp:145-161 (entry k in storage order to lane k mod activity_lanes(n), dd_add_product per lane, the merge tree) over the bounds of the moment. After a step the rows whose activity can have changed (a bound of one of their columns moved, a column was fixed, an entry or the row changed) are folded again; folding lazily before the first reader gives the same value and either executor may do so. There is no two-term update, no stale test, no second attempt after a fresh summation; updates is the number of finite terms, max_term the largest |a * bound| among the present terms. The infinite-term count is a uint16_t array per side that saturates at 65,535 (only 0, 1 and "more" are read; nothing is decremented). inf_slot leaves the state: in a row with exactly one infinite term the entry that holds it recognises itself (is_infinite_term of its own term). This is the owner's rule "never recomputed in a different order on another engine", taken literally.
C3 Work lists are sets. A mask per row and column (the pending arrays that exist) says which lists it is on; a family serves its set in ascending index. The host keeps the vectors of today and sorts at take; the device compacts the mask. The order "first event since the consumer last took it" (state.hpp:109-154) is gone, and with it from the state hash.
C4 The layout is not state. Slots, capacities, tombstones and twins are how an executor stores the canonical content. Decisions that read the layout today are redefined on counters: a rebuild happens when the entries deleted since the last rebuild exceed rebuild_dead_fraction times the entries at that rebuild, or fixed_nnz exceeds rebuild_fixed_fraction times live_nnz, and fixed_terms_absorbable holds. state_hash covers rows as sequences of live (column, value), sides, bounds, flags, activities, masks, family data and counters, not slots.
C5 One order for sums into one cell. When several reductions of one step add terms to the same cell (the cost of a column, a coefficient of a root, a side shift, the objective offset), the terms are folded in ascending index of their source (the substituted column, the pivot row, the fixed column) by the same lane fold as an activity, and tests such as the cancellation test are made on the folded sum. Today these are plain or compensated sums in application order (inventory, section 4, items 7 to 10).
C6 Records. The record stack is ordered by step and, inside a step, by the index of the unit (row or column) that the record belongs to; pool offsets are prefix sums in that order.
C7 Budgets. Work is counted per step from its frontier (8 per line, 1 per entry, as today) and the budget is tested between two steps, never between two lines. A step is done in full or not at all.
C8 Family data that outlives a call (implied-bound records with source row and version, the 16 steps per explicit bound, growth factors, the count of saved entries, keys of the parallel rows) stays, defined by maximum, minimum or sums in unit order, so that it too is a function of the steps taken.

3. THE STEP
FIND: a map over the frontier (rows or columns) that reads the frozen state and writes candidates. SELECT: one of three rules. APPLY: writes. UPDATE: sizes, free sizes, singleton counts, locks and activities of the touched lines are recomputed (they are functions of the stores, sides, bounds and flags: inventory, finding 1), the masks of the consumers are set, a status record (findings, records, work of the step, size and nonzeros of every next frontier, outcome) is produced.
The three rules for candidates that meet in one cell:
K1 Combine. All candidates are applied; writes to a shared cell are combined by an operation that is exact in any order: maximum or minimum of doubles (bounds), integer sums (locks, sizes, counts), flags. On the device the group of threads that owns the cell (the column in the binned CSC, as in cuOpt's load-balanced column kernel) reads every candidate addressed to it and reduces; counters and flags use integer atomics. No floating-point atomic and no candidate array of nonzero size. Used by: row rules, propagation, tightening, dual fixing, dual bound strengthening, implied integers, the sides of merged parallel rows, bound transfer to a root.
K2 Ordered fold. Terms for one cell are brought together by a stable radix sort on a unique integer key (cell, source index) and each run is summed in ascending source index by the lane fold. This is "reductions instead of atomics" for sums. Used by: substitution of aliases (coefficients, side shifts, costs), the cost updates of free singleton columns, the objective offset of every family.
K3 Reservation by smallest index. A candidate that needs a cell alone (a row it deletes or rewrites as a whole, a column it removes) writes its unit index into the cell's slot with an integer atomic minimum; read claims go to a second slot. A candidate is applied in this step when it holds every cell it claims and no smaller writer holds a cell it reads. A loser leaves no trace, stays on its list and is found again in the next step. The result is a function of the candidate set. Used by: the singleton-column family, the subtraction of an equation from a parallel row, implied equations, parallel-column pairs, the dominated-column rule, the lock alias.
Chains. A dependency between two reductions costs one more step (a round). Steps with a small frontier go to the host executor (section 7), so a deep, narrow chain costs host time proportional to its work, as today. The alias forest is not resolved by rounds of single edges: the whole forest is taken in one step (section 4).
Shared arithmetic. numerics.hpp gets the macro GPRS_HD (empty on the host, __host__ __device__ under nvcc), as the Stage 1b design proposed; each family gets a header of functions of values (row_class, row_candidate, tighten_row, compare_cores, edge_map, ...) used by both executors. The device code is compiled with fused multiply-add contraction off; the only fma is the explicit one in two_prod. Whether nvcc accepts the std:: math calls of numerics.hpp in device functions is unchecked (first item of milestone 0).

4. THE FAMILIES AS STEPS (details per part are in the field per_part)
State build and start step: maps, a histogram, a prefix sum, one stable radix sort, integer sums, the lane fold. No conflicts.
Row rules: FIND classifies every listed row from the stored activities (empty, infeasible, redundant, singleton, forcing); K1: all classified rows are deleted, the bounds of singleton rows and the fixings of forcing rows are combined per column by maximum and minimum, a crossing by more than the tolerance is infeasible. One step is one round; the call repeats while its list is not empty.
Bound propagation: FIND computes, per listed row and readable side, the candidate of every free entry from the stored activity (candidate_of_finite_rest unchanged); K1: per column the largest lower and the smallest upper candidate with the smallest source row among equals; integer columns are tightened, continuous columns get a record, a mark or, after make_explicit, the bound. One step is one Jacobi round.
Row tightening: a map over rows; a row edits itself only (its CSR values, their twins, its sides). No selection. The scale search is redefined so that it does not depend on the order inside the row: every coefficient gets its own denominator by the continued fraction of today, the scale is their least common multiple (integer reduction, refused above max_integral_scale), then the gcd (integer reduction) and the drift as a lane fold.
Dual fixing by locks: a map over columns, O(1) each; fixings applied together; records and the offset by C6 and K2.
Parallel rows: keys by a map (an integer sum per row, exact in any order), a sort of (hash, core length, row), then up to parallel_bucket_limit comparison rounds in which every row of a bucket that has no class yet is compared exactly with the bucket's leader, the smallest such row (the scheme of PaPILO and cuPSLP; with C1 the comparison is a merge walk of two sorted cores). A class without singleton columns is merged into its smallest row: the images of the sides are combined by maximum and minimum (K1), the other rows are deleted. A class with singleton columns gives subtraction pairs by today's rule (fewest singleton columns, then smallest index); an equation with a singleton column serves one target per step (K3).
Aliases (doubleton equations, simple probing, lock alias; one machinery): FIND gives edges. The tree edges are the minimum spanning forest of the edge graph under the key (row, column), which is unique; the host finds it by union-find over the edges in ascending key (today's code on a sorted list), the device by Boruvka rounds with an integer minimum per component. The root of a tree is the column with the best key (integer before continuous, most admissible edges, most live entries, smallest index: today's order, computed by two tree sweeps). Maps are composed from the root level by level (parents before children, today's association order); an inadmissible edge makes its child a root of its own subtree, as today. The device walks levels; after 16 levels the rest of the walk is done by the host executor on the forest arrays (they are small: the measured depth is 1 for 72.1% of the substituted columns, at most 6 at the 90th percentile of instances, 741 on CMS750_4). Substitution of all trees is one K2 step: every entry of a substituted column becomes an entry of its root with the scaled value, the entries of the touched rows are sorted by (row, new column, old column), runs are folded, side shifts and costs are folded per row and per root. Trees never wait for each other: under any rule that gives a row to one tree per batch only 32% of the trees fit a first batch (measured), under K2 all do.
Singleton-column family: FIND per row with a singleton column and per listed column; per row the first reduction that fits, as today; K3 on the rows a unit deletes or rewrites; cost updates of columns shared by several pivot rows by K2; growth factors by maximum; the limit on saved entries by a prefix sum in unit order.
Rules that are designed and not built: section 12 and per_part.
Storage: compaction is a stream compaction per line; a rebuild is a compaction of the CSR, a stable radix sort for the CSC and the fold of the fixed terms into the sides; both keep C1.
Output: two compactions (rows, columns), a gather of the entries with the new column index (no sort by C1), the fixed terms folded into the sides.
Hash: model_hash becomes a function that a reduction can compute: per array the sum modulo 2^64 of mix(position, bits of the element), with the splitmix64 finaliser as mix, and the twelve array hashes with their lengths chained by today's hasher. The chain of today stays as an option for comparisons with stored runs.
Driver: host code. The sequence of phases is today's (presolve.cpp:293-367, 409-468).

5. DEVICE STATE (details in the field data_layout)
The device holds the same line stores as state_t (start, used, capacity, size, index, value, twin for CSR and CSC), in index order, plus two scheduling lists (rows and columns by length class, made by a stable partition) in place of physically binned storage. With identical layouts a hand-over between executors is a copy of arrays or of ordered dirty records, and "device equals host" can be tested array by array. Classes: up to 64 entries in lane groups of 2 to 32 lanes of a warp, 65 to 8,192 one block of 256 threads, longer lines the same block for the fold (256 lanes for every row above 64 entries, numerics.hpp:153-161) and chunks for order-free reductions. Persistent memory about 40 bytes per nonzero, 100 per row, 90 per column; sort scratch up to 32 bytes per nonzero.

6. HYBRID RULE (details in the field hybrid_rule)
Three regimes by the free nonzeros N at call entry and the mirror size: N below N0 (provisional 1e5): host executor for the whole call. N from N0 with a state of at most 128 MiB: the device builds the state and runs every step whose work is at least T (20,000 work units for cascade steps, 200,000 for structural steps, provisional); when a step falls below T the state is handed to the host executor once, and it returns to the device only for a step of at least 16 T. Above 128 MiB: every step on the device, no host mirror. All constants are in work units or bytes; nothing is read from the machine; none can change a result.

7. IDENTITY (details in the field identity_rule)
Same bits with and without a GPU, on every GPU type, for every threshold. Not the same bits as today's engine; the gate against today is on reductions.

9. VERIFICATION (details in the field verification)
The host executor is the reference: every existing check (oracle, structure, crush, second presolve, the 99 wrong engines) runs on it. The device executor is tested by equality of the hash of the canonical state after every step. The campaign gets a union mode so that a device can run it at a useful rate.

11. THE CHEAP COLUMN RULES THAT ARE NOT BUILT
Write them directly in the batch form, not first as sequential rules. Reasons: (a) a batch step is a legal family of today's engine (the prototype runs two inside it: candidates on the frozen state, then state operations in ascending index), so they can be built now and need no second version; (b) their designs already demand what a step demands ("every premise computed at application", ties to the smaller index, one transaction per binary); (c) a sequential version would have to be gated, reviewed and attacked by wrong engines once, and again after the port. What changes against the designs in P/stage1c_design: the visit order "index order, each column once per call" becomes "all candidates of the step, then K1, K2 or K3"; caches that a fixing clears (the prices of the dominated-column rule, AS-303) become values computed per step. Simple probing as built at edd147a7e already collects on an unchanged state and applies after the last visit; only its refusal of a row whose columns the batch already connects is replaced by the spanning forest.

12. WHERE THIS ANGLE BREAKS, OR COSTS
- Today's hashes change, once, at G2 and G3. Every stored hash and the phase hashes are replaced.
- The host path gets slower than today's engine where no device helps: the prototype says up to 12% for the cascade part; C1 (sorted rows after substitutions), C2 (a fold per touched row in place of a two-term update) and sorted takes add cost that I did not measure. C2 is bounded by the fact that a touched row is scanned by propagation or tightening anyway.
- Two implementations of every step exist (loops and kernels). Shared functions of values keep the arithmetic single; the scheduling is double.
- Work that is sequential inside one line or one tree stays sequential: a 256-lane fold of a row of millions of entries (9,400 entries per thread at 2.4 million), the levels of a deep alias tree, the prefix test of column stuffing inside a row. These run as one thread or one block per line on the device, or on the host by rule.
- Chains with a wide frontier in every round would cost a full device sweep per round. None of that kind shows in the 240 (neos-1122047 has 209 lists of a median of 2,608 rows), but the nine large instances are not measured.
- K3 delays losers by a step. Measured under the strict rule 92.3% of the singleton-column units fit the first batch and the longest call needs 62 batches.
- The parallel-row leader rule and the order-free scale of row tightening are new rules, not re-orderings; their effect on reductions is unmeasured.

--- 3
part: Row rules (empty, infeasible, redundant, singleton and forcing row)
runs_on: Both. Device when the work of the step (8 per listed row plus its live entries) is at least 20,000 units (provisional), host below.
device_algorithm: FIND: a kernel over the listed rows reads the stored activities and gives a class per row; rows that need a scan (empty with fixed terms, singleton, forcing accepted in O(1)) are scanned by the lane-group or block that owns the row; a singleton row stores its two bounds in a per-row scratch. Columns of singleton and forcing rows are flagged and compacted. A column kernel over those columns reads the classes of its rows and reduces the largest lower and smallest upper bound (the fixing of a forcing row is the pair value, value). APPLY: rows deleted by flag, bounds written by the thread group of the column, fixed columns recorded by a compaction, the offset folded. UPDATE: rows of changed columns are flagged and folded again, free sizes and locks recounted, masks set. One round is about 10 launches, one or two compactions and one read-back, 100 to 150 microseconds fixed (from the Stage 0 figures of 9.0 microseconds per launch and 77 to 93 for a step of 8 launches). The call repeats rounds while its list is not empty.
why_host: Rounds below the threshold: lists below 100 rows are 1,458 of 2,263 lists with 0.1% of the work; 96.1% of the calls with a finding have a chain of at most 3 and the longest is 183 (irish-electricity), so the tail is many tiny rounds.
same_result_as_today: Not bit for bit. The same tests on the same arithmetic, but every row of a round is tested on the state at the start of the round. Measured with propagation in the same form (prototype, 240 dumps): hashes equal on 234, no instance larger, rounds +5.7%, work +1.1%.
conflict_rule: K1: all deletions together; bounds per column by maximum and minimum; lower above upper by more than the feasibility tolerance is infeasible, a smaller crossing fixes the column. Two forcing rows that fix one column at different bounds are infeasible by this rule.
expected_gain: 5.1% of the seconds today; the first list of the first call holds 72.7% of its work and lists of at least 10,000 rows 92.8%.

--- 4
part: Bound propagation and the switch to explicit bounds
runs_on: Both. Device when the work of the round is at least 20,000 units (provisional), host below. make_explicit is one map over columns on the executor that owns the state.
device_algorithm: One Jacobi round. Activities are stored values (C2), so there is no fold in the round. A column kernel over the columns of the listed rows (flag and compaction, or all columns in a full sweep), binned by length as in cuOpt's load-balanced code: per entry in a listed row and per readable side the candidate of candidate_of_finite_rest with its slack; the entry whose own term is the single infinite term takes the finite sum as it is; the group reduces the largest lower and the smallest upper candidate with the smallest source row among equals. The same group applies: integer column rounded and tightened, continuous column recorded or marked, after make_explicit tightened at most 16 times per bound. Crossing candidates are infeasible. UPDATE as for the row rules. About 10 launches, one compaction, one read-back per round. Review rules of PR 2372 kept: counts in uint16 arrays, counted in the scan, residual first, error guard, kernel variants benchmarked.
why_host: Rounds below the threshold. Lists below 1,000 rows are 1,445 of 2,122 lists and hold 8.7% of the propagation work on the 240 (4.5% on the 30 instances from 1e6 nonzeros). The longest call has 209 lists of a median of 2,608 rows (neos-1122047).

part: Row tightening (integral scaling with gcd, side rounding, coefficient strengthening)
runs_on: Both. Device when the work of the step is at least 20,000 units (provisional), host below.
device_algorithm: A map over the listed rows by lane groups and blocks. Per entry its own denominator (continued fraction, limit 1000), per row the least common multiple and the gcd as integer reductions, the drift as a lane fold, the sides rounded, then coefficient strengthening per entry from the stored activity and the new side as a lane fold of the changed terms. --- 7
part: Parallel rows: merge of two parallel rows, subtraction of an equation from a row parallel to it up to singleton columns
runs_on: Both. Device when the entries of the listed rows are at least 200,000 work units (provisional), host below.
device_algorithm: Keys: a map over the listed rows, the hash as an integer sum over the core entries (exact in any order). Buckets: cub radix sort of (hash, core length, row), boundaries by a comparison of neighbours and a scan. part: Doubleton equations with the alias forest and the substitution (the alias machinery, also used by simple probing and the lock alias)

device_algorithm: FIND: a map over listed equations with two free entries gives edges with the key (row). Forest: minimum spanning forest by Boruvka rounds (integer minimum of the edge key per component, hooking, pointer jumping on component ids only). ======== HYBRID_RULE ========
The executor of every step is chosen by the driver from numbers that are functions of the model and the settings. Nothing is read from the machine (no free memory, GPU type, core count or clock).

Work of a step: W = sum over the lines of its frontier of (8 + live entries of the line), the work unit the engine counts today. W is known before the step: the status record of the previous step carries the size and the nonzeros of every next frontier (one integer reduction).

Regimes, by the free nonzeros N of the input and the bytes B of the state (40 per nonzero, 100 per row, 90 per column):
1. N below N0 (provisional 1e5): the host executor does the whole call and no device function is called. Measured reason: a whole presolve takes the host 1.7 ms in the median below 5e4 nonzeros (93 of the 240 benchmark instances, node) and 15.3 ms between 5e4 and 2e5 (50 instances); a device call has a floor of about 3 to 5 ms (state build 0.5 ms fixed, 20 to 30 wide steps of 0.1 to 0.15 ms, structural steps of 1 to 3 ms, one hand-over). The requirement "better than HiGHS from 50,000 nonzeros" is carried by the host path there (6.9 times faster than HiGHS with the same rule set on the 40 testbed instances, an earlier version).
2. N from N0 and B at most B_mirror (provisional 128 MiB, about 3e6 nonzeros): the device builds the state and owns it. A step runs on the device while W is at least T_down of its family. At the first step below T_down the state is handed to the host executor (the mirror arrays are filled then, in one copy), which continues. The state returns to the device only for a step with W of at least T_up = 16 T_down, or for the output when the reduced model is wanted on the device. T_down: 20,000 units for the cascade families (row rules, propagation, tightening, dual fixing and the cheap column maps), 200,000 for the structural steps (parallel rows, alias machinery, singleton columns, rebuild). All provisional.
3. B above B_mirror: no host mirror; every step runs on the device, small ones too. Measured reason: on the 30 benchmark instances from 1e6 nonzeros, the calls that take the host less than one fixed device step (85 microseconds) would cost 0.3% of the engine seconds at one step each, and calls below 20,000 units hold 0.4% of them; a mirror of that size costs 0.38 s per GB to pin and a copy of the whole state. Exception inside this regime: the level walk of an alias tree beyond 16 levels and the legacy chain hash, which work on small arrays copied to the host.

What goes to the host by this rule, with the measurement behind it (240 benchmark instances, Mac seconds, measurement report): calls below 20,000 work units are 64.9% of all calls and 0.6% of the engine seconds (5.6% below 5e4 nonzeros, 0.6% from 5e4 to 5e5, 0.9% from 5e5 to 1e6, 0.4% from 1e6); 72.8% of the calls take the host less than 85 microseconds and would cost 4.4% of the engine seconds at one device step each (63.7% below 5e4, 12.2% from 5e4 to 5e5, 6.9 times the whole engine time on unitcal_7). So small models, short work lists and the last rounds are host work, and the rule sends them there.

Fixed costs the thresholds stand against (one H200, Stage 0 report section 6): kernel launch with synchronisation 9.0 microseconds; with an 8-byte read-back 13.8; reduce, compaction or scan up to 1e5 elements 23 to 46; sort of 1e3 to 1e5 elements 94 to 501; a step of 8 launches, one read-back and one compaction 77 to 93; hand-back with an ordered dirty list and a mirror at most about 141; pinned copy 52 GB/s; pinned allocation 0.38 s per GB (so the mirror pool is created once with the context, outside the timed call). Host cost per work unit by family (node, 240): propagation 9.7 ns, doubleton 7.2, row rules and tightening 5.1, parallel rows 3.4, singleton columns 2.1, dual fixing 1.1. A cascade step of 10 launches (100 to 150 microseconds) therefore breaks even between 10,000 and 30,000 units; 20,000 is the plan's provisional value.

Because both executors give the same bits, N0, B_mirror, T_down and T_up cannot change a reduced model, a record or a work count. They are options with one shipped default each, fixed once at the last milestone by the rule of AS-307 (smallest summed time over the 240 and the testbed, ties to the host, no instance slower than the host path by more than the larger of 5% and 2 ms on the smallest of three alternating runs). On Grace Hopper the host executor works in place on managed memory and regime 3 would not need its exception; the shipped rule is the same on both machines so that the schedule of executors is the same everywhere, and lifting the cap there is a switch that changes time only.

Not known: N0 after integration (the device build wins from 1.3e6 nonzeros in the measured, not integrated form; without host vectors it should win far lower, which is an expectation); how many hand-overs a call makes (I expect one: the first calls hold 74 to 94% of every family's work); the fixed cost of the structural steps, which I estimated from launch and sort counts.

======== IDENTITY_RULE ========
Between a run with and without a GPU: equal in every bit. For the same model and settings, the reduced model, the record stack, every statistic counted in work units or findings, the status, and the hash of the canonical state after every step are the same for: a build without CUDA; the host executor forced; the device executor forced; the hybrid rule with any thresholds; the pinned path on x86 and the managed path on Grace Hopper; any GPU type; any run and any co-running load. This follows from the construction: every step is one function with one arithmetic (shared functions of values, fused multiply-add contraction off, explicit fma in two_prod only), every floating-point sum has one order (lane fold), conflicts are resolved by index and value, and sorts have unique keys. I agree with the preference for the same bits with and without a GPU: it is what lets the oracle, the structure and crush checks, the 99 wrong engines and the random campaign test the device path through the host path, and it makes every threshold a matter of time only. The cost is that the bits are bought by changing the host engine, not by making the device follow today's order.
What differs between such runs by design: seconds, and the device counters (launches, read-backs, bytes moved, hand-overs).

Between GPU types: equal, on the same grounds; no library reduction of a floating-point sum is used (CCCL guarantees the same sum across GPU types only for the plain reduction, not the segmented one: research report 4g), class boundaries and lane counts are constants, and nothing is tuned per architecture. Tested, not assumed (verification).

Between today's engine (commit 04692babd) and the new one: not equal in bits; the gate is on reductions. Where the reduced model can differ, and what is known:
1. Row rules and propagation as rounds on the state at the start of the round, lists in ascending index, budget between rounds. Measured by the prototype on the 240 benchmark dumps: status equal on 240, hash equal on 234, rows 10,472,693 to 10,472,626 (momentum1 65 fewer, neos-1122047 2 fewer), columns equal, nonzeros 101,227,465 to 101,227,331, no instance larger in any measure, fixed point on 234 in both. Four of the six differing instances have the same sizes (app1-2, satellites2-40, satellites2-60-fs, supportcase12). On the 17 small local dumps all hashes are equal. Ascending lists alone change 2 of 240 hashes.
2. Activities summed from scratch in place of accumulated ones (C2): the error bound is the smallest possible, so a guard passes at least as often; candidates of continuous columns can differ in the last bits. Not measured.
3. Sums in a fixed order (objective offset, costs and root coefficients in substitutions, side shifts): last bits of the reduced model on instances where one cell takes several terms. Not measured; no reduction depends on it except through the cancellation test, which is made once on the folded sum.
4. Canonical row order after substitutions: changes the lane of entries in later folds, so last bits. Not measured.
5. Parallel rows by leader rounds: classes of mutually parallel rows give the same merges; buckets with more unlike classes than parallel_bucket_limit can end differently, either way. Not measured.
6. Row tightening with an order-free scale: can find a scale where today's search does not, or the reverse. Not measured.
7. Singleton columns under reservation: a loser waits one step; a loss is possible only where a budget ends the call first. Not measured.
8. Continuous bounds after make_explicit: rounds take more and smaller steps (neos-1122047: 72,403 to 156,923 propagation findings), so the 16 steps per bound can be used up earlier and the call reports limited. Seen on one instance, with 2 fewer rows, not more.
How it is measured at the gates: rows, columns and nonzeros of the reduced model against today's engine on the 240 benchmark instances and the 40 testbed instances, as the geometric mean of new over today and per instance; every instance that is larger by more than 0.5% in any measure is explained; the gate against the HiGHS reference (today 1.002 of the ladder reference) is run again. An instance where the new engine removes more is listed, not failed (amendment A1).

What replaces the test "equals today's stored hash": for the host executor, the reduction gate above plus the oracle campaign, the structure and crush checks on the 240 and the testbed, the second-presolve test and the wrong engines; from then on new stored hashes. For the device executor nothing is replaced: it is tested by equality with the host executor after every step.

======== DATA_LAYOUT ========
One layout for both executors, so that a hand-over is a copy and equality can be tested array by array.

Matrix. CSR and CSC as the line stores of state_t (state.hpp:62-75): per line start (int64), used, capacity, size (int32); per slot index (int32, -1 for a tombstone), value (double), twin (int64, the slot of the same entry in the other store). Live entries of a line are in increasing index of the other dimension (C1). Storage is in index order, not binned; two scheduling lists (row ids and column ids ordered by length class, 4 bytes per line, made by a stable partition after every build, compaction or rebuild) give the kernels their classes: 1-2, 3-4, 5-8, 9-16, 17-32, 33-64 entries as lane groups of a warp, 65 to 8,192 one block of 256 threads, above that the same block for the fold (256 lanes) and chunks of several blocks for maximum, minimum and integer reductions. Whether in-place storage with lists is as fast as physically binned storage is not measured (AS-309 says the binned layout itself is unmeasured in place); the choice cannot change a result.

Rows. row_lower, row_upper (double), row_alive (uint8), row_free_size, row_singletons (int32), row_version (uint32), the list mask (uint16), and per side of the activity: hi (double), lo (double, its own array), max_term (double), infinite-term count (uint16, saturating, its own array). The count of finite terms is the row size less the infinite count and is not stored. About 100 bytes per row.

Columns. col_lower, col_upper, cost (double), type, status (uint8), down_locks, up_locks (int32), the implied-bound records (two doubles, two int32 rows, two uint32 versions), the list mask (uint16), family data (pending and step marks of propagation, growth factor, key of the parallel columns). About 90 bytes per column.

Deletions. A deleted row is a flag; its entries are dead in both stores without a write (an entry is live when its slot is not a tombstone, its row is alive and its column not removed). Single deleted entries are tombstones in the CSR and, through the twin, in the CSC. Sizes, free sizes, singleton counts and locks are recounted for the touched lines at the end of the step. Compaction of a line when it has more tombstones than live entries, as today. Rebuild by the counter rule of C4: CSR compaction, fixed terms into the sides, CSC by the stable radix sort, insertions of the step merged in column order.

Work lists. The masks above; a step compacts the mask of its list into an index buffer (4 bytes per line, two buffers) or runs over all lines when the frontier is everything.

Scalars and status. The objective offset (hi, lo), counters, and one status record per step (findings, records, work, size and nonzeros of each next frontier, outcome with the smallest index that caused it), written with integer atomics and read back once per step.

Record stack. Device arrays per record kind plus the order array and the pool of saved entries (int32 index and double value per entry), appended per step in unit order; copied to the host at the end or when a byte limit is passed. The pool can reach opt.saved_row_factor (4) times the input nonzeros in the worst case; dlr2 saves 71 million entries (0.85 GB).

Memory. Persistent: 40 bytes per nonzero (two stores of 4 + 8 + 8), about 100 per row and 90 per column. Scratch: a radix sort of 64-bit keys with a 64-bit payload needs two buffers, at most 32 bytes per nonzero for a full rebuild. For 2.57e8 nonzeros that is 10.3 GB plus 8.2 GB of scratch; for 1e6 nonzeros 72 MB. Sizes are planned from the model before the first allocation (one slab each for matrix, state, scratch and staging, as the Stage 1b design proposed); a need above the byte budget makes the call host-only, from the model and the settings alone. Twins as int32 when the slots fit would save 8 bytes per nonzero; not proposed as the default because the mirror would then differ from state_t.

What is mirrored on the host, and how it is kept current.
x86 with a discrete GPU. Device arrays from cudaMalloc. In regime 2 (state at most B_mirror) the host state_t takes its arrays from a pinned pool of the presolve context, created once outside the timed call (pinning costs 0.38 s per GB). One executor owns the state at a time. At the first hand-over to the host all arrays are copied (128 MiB at 52 GB/s is 2.5 ms). Later hand-overs carry dirty records in ascending index through the pinned staging buffer: a row record (index, sides, flags, both activities, mask), a column record (index, bounds, cost, flags, locks, marks), an entry record (slot, index, value); the owner keeps the marks and lists of what it changed since the last hand-over (a journal that no rule reads and no hash covers); when more than one eighth of an array is dirty the array is copied whole. In regime 3 there is no mirror; the host holds the input model, the records and, at the end, the reduced model.
Grace Hopper. cudaMalloc memory is not host-accessible there, so the same arrays live in one managed slab aligned to 2 MiB with preferred location GPU and accessed-by CPU. The host executor waits for the stream and then reads and writes the arrays in place; a hand-over copies nothing. The path is chosen by the device attribute for direct managed access and can be forced on x86 for tests. All engine code above the two functions host_access and release is the same on both paths. No time or memory figure is claimed for Grace Hopper: nothing was measured there.

Without CUDA. The host state_t on ordinary memory and the host executor are the whole engine; the device project stays a separate CMake project as today.

======== VERIFICATION ========
1. The host executor is the reference and takes every existing check unchanged: the unit tests (473 today; those that assert a visit order or a stop inside a list are rewritten for steps, 7 failed under the prototype for that reason), the oracle campaign of tools/gprs_fuzz.cpp (optimum by enumeration, structure check, crush check, second presolve of a fixed point), the structure check on the 240 benchmark instances and the testbed in the assertion build, and the 99 wrong engines of check/make_mutants.py, each of which must still be caught by a named check after the rewrite (their patches are ported to the batch code; a wrong engine that no longer applies is replaced by one for the new code: a dropped tie-break, a reservation that ignores read claims, a fold in the wrong order, a missing refold of a touched row).

2. Every device step is tested against the host step by the hash of the canonical state and of the record stack after the step (options_t::phase_hashes extended from phases to steps). The harness runs both executors on the same input, compares the hash sequences, and at the first difference dumps both states and names the first array and index that differ. Three forms: (a) step by step from the host state (the device gets the host state before each step, so one wrong step shows alone); (b) the device executor forced for the whole call; (c) the hybrid with thresholds drawn at random per call, including 0 and infinity and a coin per step, which also tests the hand-overs in both directions. Run on the unit-test models, the 240, the 40 testbed instances including the nine above 1e7 nonzeros, with the pinned and the forced managed path.

3. The campaign through the device. A device step costs about 100 microseconds, so single models of 20 rows would run at a few hundred per second against 760,000 on a node. New in the tool: a union mode that concatenates K random models into one model with disjoint rows and columns, presolves the union once with each executor, compares the step hashes, and runs the oracle per block on the result (a valid reduction of the union restricted to a block is a valid reduction of the block). The union also exercises long lines and many classes at once when models with long rows are mixed in. With unions of 1e5 models the device throughput is the host throughput times the device gain, so a billion models is a matter of hours on one GPU; that figure is an expectation. A second new mode draws the executor schedule per seed as in 2(c) on single models at a low rate, for the hand-over code.

4. Kernel tests in the device project (as G/device/test does for the state build): every kernel against the shared function of values on all length classes, including rows of 0, 1, 64, 65, 8,192, 8,193 and more than 65,535 entries, rows with 0, 1, 2 and more than 65,535 infinite terms, tombstones at every position, MIP variable types as the review of PR 2372 asks. Every kernel variant is benchmarked against the one it replaces before it goes in.

5. Wrong engines for the device: at least one per kernel family (lanes merged in another order, an entry skipped at a class boundary, a floating-point atomic in place of the fold, the tie-break of a reduction dropped, a dirty row not folded again, a stale mirror after a hand-over). Each must be caught by the step-hash comparison on a named model.

6. Determinism across runs and GPU types: the step-hash sequences of the 240 and the testbed, three runs each, with a co-running GPU load, on two GPU types and on a Grace Hopper node with the managed path, all compared with the host-only build. Zero differences is the criterion. A second GPU type has not been measured in this project yet.

7. Against today's engine: the reduction gate of the identity rule, once at each milestone that changes the host algorithm.

8. What I did in this round with the prototype (batch rounds for row rules and propagation): 45 million random models without a failure (28.8 million on the first version, then 7.2 million default profiles, 7.2 million with --singletons --columns and 1.8 million in the assertion build on the final version), the 473 tests pass with the switch off, and with it off the 240 hashes equal the stored node run. Not done: the wrong engines against the prototype, and any larger campaign.

======== REDUCTIONS_LOST ========
Measured, for the part of the design I could prototype (row rules and bound propagation as batch rounds on the state at the start of the round, lists in ascending index, budget tested between rounds; 240 benchmark dumps, scratch copy of commit 04692babd, release build on this Mac): nothing is lost. No instance has more rows, columns or nonzeros than today's engine. Two instances get smaller: momentum1 by 65 rows and 130 nonzeros (24,254 to 24,189 rows), neos-1122047 by 2 rows and 4 nonzeros. Columns are equal on all 240. The reduced-model hash is equal on 234 of 240 (the other four that differ, app1-2, satellites2-40, satellites2-60-fs and supportcase12, have the same sizes). Fixed point reached on 234 in both. On the 17 small local dumps all 17 hashes are equal. Ascending lists alone change 2 of 240 hashes and no size beyond neos-1122047.

Not measured, with where a loss is possible and how large I expect it:
- Parallel rows by leader rounds: a bucket that holds more than parallel_bucket_limit classes of unlike rows can leave a pair unmerged that today's scan of four neighbours on each side finds, or the reverse. Buckets are sets of equal hash and core length, so this needs hash collisions or near-parallel rows; I expect a handful of rows on the 240, in either direction.
- Singleton columns under reservation: a unit that loses a row is found again in the next step; a loss needs a budget that ends the call first. 16 tightening calls and 4 others stop on a budget on the 240 today, none of them of this family.
- Row tightening with the order-free scale: can differ from today's search inside a row in either direction; unknown size, probably single rows.
- Continuous bounds after the switch to explicit bounds: rounds take more, smaller steps (neos-1122047: 72,403 to 156,923 propagation findings), so the limit of 16 steps per bound can end a chain earlier. On the 240 this showed as no loss.
- Activities summed from scratch, sums in a fixed order, sorted rows: last bits of continuous bounds, sides, costs and the offset; I expect no change in rows, columns or nonzeros beyond single tolerance cases.
- The nine instances above 1e7 nonzeros and 14 of the 31 testbed instances below were not run with the prototype.
Each of these is measured at the gate of the milestone that introduces it (G2, G3), on the 240 benchmark instances and the 40 testbed instances, as the geometric mean and per instance of rows, columns and nonzeros against today's engine, with every instance above 1.005 explained.

======== RISKS ========
- The host path of the new engine is slower than today's where no device helps. The prototype shows +11.8% engine seconds on the 240 (smallest of 5 runs, loaded Mac, untuned), and activities summed from scratch, sorted rows after substitutions and sorted takes add cost that is not measured. If the sum passes the 1.10 gate, the design needs a cheaper host form of C2 (lazy folds) or the owner has to accept a slower host-only path below N0.
- Two implementations of every step double the code that carries scheduling (loops and kernels). A change of a rule must be made in the shared functions; where a rule cannot be written as functions of values, the two executors can drift, and only the step-hash test catches it.
- Bit equality between the host compiler and nvcc is assumed for IEEE double operations with contraction off and an explicit fma; whether nvcc accepts the std:: math calls of numerics.hpp in device functions is unchecked, and a difference in a library function (round, ceil, the continued fraction) would break identity on some inputs.
- The alias machinery on the device is the largest single piece (spanning forest, levels, sort and fold, insert path of the rebuild) for a family that is 4 to 6% of the time. If it slips, the hybrid rule can leave this family on the host in regime 2, but in regime 3 there is no mirror, so the piece is needed for the large instances or regime 3 needs a mirror after all.
- Chains with a wide frontier in every round would cost a full device sweep per round. The 240 show none, but the nine large instances were not measured for depth (sesia and dlr2 have later calls of the row rules and propagation with 46 to 62% of the work).
- The thresholds come from one H200 and a loaded Mac. They cannot change a result, but wrong values can make instances between 1e5 and 1e6 nonzeros slower than the host path; the gate catches it only at G4.
- The mirror regime needs pinned memory of up to 128 MiB per presolve context and a first hand-over that copies the whole state; inside cuOpt, where several presolve calls (sub-MIPs) can run, the pool policy is not designed here.
- The saved-row pool and the record arrays live on the device until they are flushed; on dlr2-like models (71 million saved entries) they are near 1 GB, and the worst case is 4 times the input nonzeros.
- The union mode of the campaign changes what a seed tests (one presolve of many blocks). A bug that shows only on tiny standalone models (a call that ends after one step) could be missed by the union and has to be covered by the low-rate single-model mode.
- Changing every stored hash at G2 and G3 removes the comparison with the stored runs of today; from then on a regression against today's engine is visible only in reductions, the oracle and the structure check.
- Grace Hopper is designed from documented behaviour only; nothing was measured there, and a second GPU type has never been run in this project.

- Parallel rows: may the bucket scan of four unlike neighbours on each side be replaced by comparison with a bucket leader for up to four rounds (the scheme of PaPILO and cuPSLP)?

======== UNSURE ========
- Whether the prototype result carries over to the full design: it has batch rounds and ascending lists for two families only, keeps today's accumulated activities, and was run on the 240 benchmark dumps and 17 small dumps, not on the nine instances above 1e7 nonzeros or the other 14 testbed instances.
- The prototype's seconds: a loaded Mac (load average 16 to 47 from other agents), smallest of 5 runs, per-instance ratios from 0.72 to 1.77. The +11.8% is an order of size, not a figure for the node.
- That dual bound strengthening can be applied to all columns of a step together (rule K1). My argument is that each proof holds for every value of the other columns inside their old bounds; I did not prove it for two columns that tighten each other, and the HiGHS code applies them one at a time.
- That the minimum spanning forest by row key equals today's tree edges whenever today's list is ascending: read from alias_forest.cpp:84-105 (union by size, edges kept in arrival order), not tested. The root score of today (most admissible edges) needs two sweeps over the tree on the device; I did not design those kernels in detail.
- The fixed cost of the structural device steps (0.6 to 3 ms) is my count of launches and sorts times the Stage 0 figures, not a measurement.
- That storage in index order with scheduling lists is as fast as physically binned storage; neither was measured in place.
- That a 256-thread block is fast enough for the fold of very long rows (9,400 entries per thread for a row of 2.4 million entries; the cuPSLP paper gives 72 ns per element for one GPU thread, as read by the research report). The Stage 1b design left a chunk rule for both engines open; if it is needed, numerics.hpp changes for rows above 8,192 entries on both executors.
- N0 and the gain between 1e5 and 1e6 nonzeros: my estimate of a 3 to 5 ms floor per device call says the device may win only from 2e5 to 5e5 nonzeros; the expected factors in the acceptance are estimates.
- Whether the order-free scale of row tightening finds the same scales as today's search on real rows.
- How many hand-overs a call makes in regime 2; I assumed one from the first-call shares (74 to 94% of every family's work).
- The 28.8 million models of the first campaign ran on the first version of the prototype (candidates collected in a list); the final version (direct reduction) ran 16.2 million. Both are the same rule; I did not rerun the large one.
- I did not read the Stage 1c design texts, simple probing at edd147a7e, the device state build, the cuOpt kernels or the papers myself; what the design says about them comes from the inventory, measurement and research reports.
