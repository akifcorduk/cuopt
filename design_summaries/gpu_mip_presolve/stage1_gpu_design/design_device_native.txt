======== TITLE ========
Stage 1 on the GPU, device-native: one wave engine whose steps have a plain C++ executor and a CUDA executor with the same bits

======== SUMMARY ========
This design takes the device-native angle to its end. Stage 1 is redefined as a "wave engine": every family is a loop of waves, a wave evaluates all rows or columns of its work list on the state as it stands, resolves conflicts by integer priorities, exact min/max reductions or sums with one fixed order, and applies everything together. Each step of a wave has two implementations with the same bits: plain sequential C++ (the host-only build and the small work) and CUDA. Because the result does not depend on which executor ran a step, the hybrid rule (model size, short work lists, last waves) can only change time, never a result, and a run with a GPU equals a run without one, on every GPU type, wave by wave.

The price is stated plainly: the result is not today's result. The order of application changes (snapshot instead of row by row), activities are always summed from scratch, rows are kept in column order, and the hash becomes a parallel one. So today's stored hashes, the 99 wrong engines as text patches and the tests of the state operations must be re-based, and the reductions must be shown again against today's engine (gate proposed: geometric mean of remaining nonzeros, rows and columns within 0.1% of today's on the 240 benchmark instances and the testbed, every instance worse by more than 1% explained). What is kept: the oracle, the campaign, the structure and crush checks, the postsolve, and the property the owner's assistant asked for, that the campaign on the host tests the device path.

What goes to the device: state build, start step, activities, all four cascade families as one fused wave, parallel rows, doubleton equations and every alias rule, the singleton-column family, simple probing, all nine unbuilt column rules, storage rebuild, record production, output and hash. What stays on the host, each with a measured reason: the driver, the record stack in order, models below about 200,000 nonzeros, waves below 20,000 work units on models whose state fits a host mirror, and small or deep alias forests.

Read: DESIGN.md lines 27-628, the Stage 1b design in full, the device entries of ASSUMPTIONS.md, HISTORY Entry 32, Stage 0 report section 6, and about 1,500 lines of the engine. Ran: two Python scripts over the stored measurement of step one (a model of the hybrid rule). Nothing was built; no wave, kernel or reduction figure of this design is measured.

1. THE DESIGN IN TEN POINTS

1. One engine, defined by its steps. A step is a data-parallel operation with an exactly defined result: a map in which every item writes only its own outputs, a gather, a scatter to unique targets, a stable sort by an integer key, an exclusive scan of integers, an order-preserving compaction, a reduction or reduction by key with an operator whose result does not depend on order (integer sum, min, max, bit-or, the lexicographic minimum of an integer tuple), the row fold (a compensated sum in the lane order of numerics.hpp:145-161), the ordered segment sum (section 3) and pointer jumping on integers.
2. Two executors per step: seq (plain C++17 in the host library, no CUDA) and cuda (in G/device). They must return the same bits for every input. The host-only build is the engine with the seq executor.
3. Waves. A family call is a loop of waves: evaluate on the state as it is (read only), select (conflict rule), apply (all together), derive the next work list. Nothing is applied while another item of the same wave is evaluated.
4. Derived data is a function of the content. Activities are never updated; a row whose entries or column bounds changed is folded again before it is read. Rows are kept in ascending column index, columns in ascending row index, so the lane of an entry is a function of the matrix, not of history.
5. Work lists are flag arrays; the list a step visits is the flagged indices in ascending order. The order 'first event since the consumer took it' is gone.
6. No floating-point atomic anywhere. Integer atomics for counters and for minimum-priority claims.
7. The state lives on the device from the state build to the output when the device is used. The host holds the driver (scalars), the record stack after each flush, and a mirror only where the hybrid rule can hand work back.
8. The hybrid rule chooses the executor of each step from work counts and the model size. It cannot change a result, only time.
9. Today's sequential engine stays in the library as engine = sequential until the wave engine has passed the reductions gate; then the owner decides whether it is retired.
10. The unbuilt column rules are written once, in wave form.

2. ENGINE STRUCTURE

2.1 Logical state (what a hash and an equality test see; the layout is free).
Matrix: the set of live entries (row, column, value). Rows: lower, upper, alive, version. Columns: lower, upper, cost, type, status (live, fixed, removed), implied-bound records (value, row, row version per side), explicit-step counters, the offset contribution (hi, lo) of the column. Scalars: model offset, counters of changes. Flags: one uint16 mask per row and per column, one bit per consumer (the 11 row lists and 5 column lists of state.hpp:159-187 keep their meaning as bits). Family data: the parallel-row key per row (hash, core length), growth factor per column, saved-entry counter.
Derived per row (the 'row summary', produced by the fold step, split arrays): min activity hi, lo, max activity hi, lo (double); count of infinite terms per side (two uint16_t arrays, exact, a saturated count marks the side as unusable until the next fold); largest finite term per side; sum of the terms of fixed columns (hi, lo) and of their absolute values; free entries, free continuous entries (int32); smallest, largest and second largest |a| over free entries; position of the single free entry. Derived per column: live entries, down locks, up locks, singleton flag. row_singletons per row. All of these are functions of the content, recomputed by the fold or kept by integer atomics, and checked against a full recomputation in assertion builds.
Gone from the state: updates and incremental bits of an activity, inf_slot as a slot sum, store capacities and moved columns, list order, the running objective offset.

2.2 Steps and executors.
The interface is one abstract class executor_t (host header, no CUDA include) with about 70 named steps, each documented with the arrays it reads, the arrays it writes and its result. Examples: fold_rows(flag), row_verdicts, tighten_rows, column_candidates, apply_bounds, apply_row_deletions, dual_fix, mark_frontier, make_explicit, key_rows, bucket_rows, compare_with_leaders, merge_parallel, collect_edges, forest (three steps), expand_aliases, combine_duplicates, rewrite_lines, rebuild, select_records, build_reduced, hash. The arithmetic of every step is in shared headers of value functions (host-and-device inline functions of numbers, no state): numerics.hpp, implied.hpp, integral.hpp, forcing.hpp as they are, plus new headers extracted from today's rule files (row verdict, entry candidates, integer bound decision, tightening of one row, key mix, edge map, singleton tests). A wrong rule is then wrong in both executors and is caught by the oracle and the mutants; a wrong kernel is caught by step equality.
Step equality is the unit of testing: both executors run the same step on the same state and every output array is compared bit for bit.

2.3 A wave, and the wave status.
Every wave ends with one read-back of a small struct: next rows, next entries, next columns, findings and work per family, smallest infeasible index, smallest unbounded index, rows deleted, columns fixed, inserts pending. The driver decides from it alone.

2.4 Driver (host, both builds).
presolve = build; start step; rounds; make_explicit and more rounds; absorb fixed terms and more rounds; output; hash, as in presolve.cpp:409-468. A round = cascade (fused waves until its flags are empty, the budget stops it or max_cascade_passes waves have run), then parallel rows, doubleton, simple probing, singleton columns, dual columns, parallel columns, each followed by end_phase (rebuild or nothing). Budgets stay in work units with the formulas of presolve.hpp:85-99; a wave charges, per family, 8 per line evaluated plus the entries read, counted by integer reductions inside the steps, the same in both executors; stop is tested between waves, so a call can overrun its limit by at most one wave. The time limit is tested between waves and only gives status limit.
Statistics keep their fields; 'calls' of a cascade family becomes the number of waves in which its flags were not empty, first_work the work of the first cascade. This changes the meaning of two reported numbers.

2.5 Sync layer.
Every array is a handle from one presolve-owned memory resource with host_access(range, mode) and release, as in the Stage 1b design. A step declares what it reads and writes; before a seq step on a device-resident state the layer brings those arrays current on the host, and the reverse. On Grace Hopper this is a stream synchronisation and nothing else (managed memory, preferred location GPU, accessed-by host). On x86 it is a transfer of dirty records in ascending index through a pinned window, or whole arrays above a share of dirty lines; the matrix is downloaded only when a host step needs it and it changed since the last download.

3. FLOATING-POINT RULES

F1. Row sums (activities, fixed-term sums, any sum over the entries of a line): the lane fold of numerics.hpp over the live entries in storage order, which is ascending column index. Rows up to 64 entries by lane groups in a warp, longer rows by one block with a hand-written tree (kernels 1 and 2 of the Stage 1b design, starting from act_light_kernel and block_fold in G/microbench/sweeps.cu). Infinite terms are counted in the scan with one integer atomic per thread only when its local count is not zero; counts are uint16_t in separate arrays; no second reduction (review of cuOpt PR 2372).
F2. Ordered segment sum: a sum over a small group of terms that belong to one target (the coefficients that several substituted columns bring into one entry, the side shifts of one row, the cost moved into one column). The terms are sorted by an integer key (origin column or origin row, ascending), added by one thread per group with dd_add_product in that order, rounded once, and tested once for cancellation with tol.cancellation. Both executors do the same.
F3. Dense sum (the objective offset): each column owns its contribution (written by its own thread when it is fixed or substituted); the offset is formed once, at the output, as a pairwise tree over the columns in index order with dd_add, the tree fixed by the number of columns and a constant leaf size. No running sum exists.
F4. Everything else that crosses lines is max or min under a total order (value, then index), an integer, or a store of a constant.
F5. Contraction off in both compilers; the only fused multiply-add is the explicit one in two_prod; sorting never uses a floating-point comparison (a double key is mapped to an ordered 64-bit integer, ties by index).
Option, for the owner: since every hash changes with this design anyway, the order for rows above 8,192 entries can be changed now to chunks of 8,192 entries, each folded as a row and merged by the lane tree. It removes the latency of one block per very long row (about 2 ms per fold of a row of a million entries, Stage 1b risk list) at no extra re-basing cost. Default in this design: the order of numerics.hpp unchanged.

4. CONFLICT RULES (how simultaneous applications get one result)

K1. Facts. A bound that holds for every feasible point (propagation, singleton row, forcing row, bound transfer of an alias) is combined per column by max of lowers and min of uppers with the tie going to the smaller row index; integer rounding after the reduction (monotone, so equal to rounding each candidate); a crossing beyond the tolerance is infeasible. A fact derived from wider bounds is weaker, not wrong.
K2. Own line. An edit that reads its own row and column bounds and writes only its own row (redundant row, tightening) or its own column (dual fixing, dual bound strengthening, scaling of a column) has no conflict. Each proof holds for any values of the other variables in the box, and the box only shrinks during the wave.
K3. Ordered sums. Writes of several units into one cell that add up in exact arithmetic (cost moved into a column by several pivot rows, coefficients merged into one root entry, side shifts of one row) are collected as (target, origin, term), sorted and combined by F2. This replaces 'one after the other in application order' and needs no exclusion. It is why all alias trees of a batch are applied at once: under any one-unit-per-row rule only 32.0% of 280,666 trees fit the first batch and 13.2% of 151 calls need more than 64 batches (240 benchmark instances, measurement of step one), although no tree depends on another.
K4. Claims. Where a unit's proof reads a cell that another unit of the wave writes (forcing column, dominated column, parallel-column dominance and merge, implied equation, single-equation fixing), units claim cells by an integer atomic minimum of their priority and commit only if they hold every cell they write and no committed unit writes a cell they read. The committed set is then equivalent to applying the units one after another in priority order with the premises true at application, which is the form the Stage 1c designs were reviewed in. Priority is the index where chains are short by construction (one winner per row or per column), and a hash of (wave, index) with the index as tie-break where chains in index order can be long (dominated columns); both executors use the same function. A unit that loses leaves no trace except its flag for the next wave.
K5. Integer counters (locks, live entries, sizes) change by integer atomics.

5. THE PARTS (the per-part list of this result has the same content with reasons and expected gains)

Build. Upload or take device arrays; column histogram and scan; stable radix sort of entry positions by column (existing G/device/src/state_build.cu, measured bit-equal); locks (existing locks_kernel); start step as two maps with a min-reduction for the first infeasible index and a compaction of the fixed columns into records; fold of every row after the start step; flags by fill; class plans.

Cascade wave (row rules, propagation, tightening, dual fixing fused; a family that is switched off is masked). (1) fold_rows on rows flagged activity-dirty. (2) row_verdicts, one thread per flagged row, O(1) from the summary, in today's order of tests: empty, infeasible, redundant, singleton row, forcing row. (3) column_candidates over the columns of flagged rows: per entry the candidate of implied.hpp on the snapshot activities, or the singleton-row bound, or the fixing value of a forcing row (as a lower and an upper candidate, the smallest forcing row index winning the value); reduced per column by K1 inside the column's thread group; the leader thread decides the integer bounds, writes the bounds or the implied record, marks the column. For small work lists the same result comes from a row-driven form (candidates of the flagged entries, sort by column, reduce by key). (4) tighten_rows on the flagged rows that were not deleted: integral scaling with the gcd, side rounding, coefficient strengthening, evaluated on the snapshot and written to the own row and, through the twin index, to the column copy. The scale search becomes per-entry denominators with their least common multiple as an integer reduction; the checks after it (rounded coefficients, drift, gcd) are today's. (5) apply_row_deletions: alive flag, lock and size decrements by integer atomics over the entries of deleted rows, singleton-column flags. A forcing row is deleted only if it won all its free columns; otherwise it is flagged again and is an empty or constant row in the next wave. (6) dual_fix over flagged columns on the locks after (5) and the bounds after (3). (7) mark_frontier: rows of changed columns, columns of deleted rows. (8) status read-back. Fixed-column records are selected once per call, ordered by (wave, column).
Chains: one wave per link. Measured on the 240 benchmark instances: 96.1% of the row-rule calls with a finding and 84.2% of the propagation calls have a chain of at most 3, the longest is 834 (neos-1122047); the chain is an upper bound taken in the host's order, the wave count in snapshot order is not measured.

Switch to explicit bounds. A map over columns with a valid record, then mark_frontier. 2,069,123 bound changes on the 240 benchmark instances.

Parallel rows. key_rows: per listed row an integer hash over the core entries (two reductions in one line kernel: the entry of the smallest core column, then the sum of mixes). Sort of (hash, core length, row) by a stable radix sort; bucket bounds by adjacent difference and scan. Up to parallel_bucket_limit leader rounds: the smallest unclassified row of a bucket is the leader, every other unclassified row of the bucket compares itself exactly with it (one thread per pair walking both rows in column order; a rank-parallel form for long rows is a variant). Per class: the kept row is the smallest index, its sides are the max and min of the images of all sides (K1 on rows); removed rows are deleted; records in ascending removed row. Subtraction of an equation: one pivot equation per class (fewest singleton columns, then smallest index, an integer tuple minimum), every admissible target deletes its core entries and gets the equation's singleton-column entries as inserts with the side shift by F2. One wave per call (chain 1 in all 172 calls with a finding).

Alias pipeline (doubleton equations, simple probing, single-lock alias share it). collect_edges: map over listed rows, compaction in ascending row. Forest: the minimum spanning forest with the row index as edge weight, which is unique; seq builds it with union-find over ascending rows, cuda with Boruvka rounds (minimum outgoing edge per component by an integer minimum, hook, pointer jumping). At a first call today's list is ascending, so today's tree edges are the same set (argued from alias_forest.cpp:84-105, not tested). Rooting and maps: breadth-first levels from the smallest column of each tree for the scores, the root by today's key (integer first, score, live entries, smallest index), levels from the root, and the composition scale[v] = map.scale * scale[parent], offset[v] = map.scale * offset[parent] + map.offset level by level, which is today's association order; a vertex whose edge is inadmissible or whose map is unusable becomes a root. Apply: bound transfer to the root by K1; expansion of the entries of all substituted columns into (row, root, origin column, moved value, side product); stable sort by (row, root, origin); coefficients by F2 with the existing root entry first; side shifts per row by F2 and one dd_residual; cost per root by F2; offset contribution per column; substituted columns marked removed (their entries are dead by status, no write); inserts merged by a line rewrite or the rebuild of end_phase. All trees in one batch. Non-tree rows are flagged again.

Singleton-column family. Per flagged row with a singleton column, one line kernel takes the reductions the tests need and chooses one unit per row: the free singleton column with the smallest index that passes (equation or inequality as pivot row), else the zero-cost singleton set. Cost changes of other columns by K3 (sort by (column, pivot row)). A unit that reads a cost which a pivot row of the same wave writes is dropped for this wave (a mark, stores of 1). Saved-row budget: exclusive scan of saved entries over the units in ascending row, units accepted while the running total is within saved_row_factor times the nonzeros, which is the sequential rule in ascending order. Forcing columns in a second half-wave with claims on their rows (K4, priority the column index). Rows are saved into the record pool by a gather with offsets from a scan.

Unbuilt column rules, storage, records, output, hash: see the per-part list and sections 6 and 7.

6. STRUCTURAL EDITS AND STORAGE

Device matrix: CSR (column id int32, value double, twin position) and CSC (row id, value, twin), rows and columns stored binned by length class in ascending index inside a class (stable sort), 64-bit offsets, 32-bit ids, positions 32-bit while the nonzeros fit. A deleted row or removed column kills its entries by status; a single deleted entry gets index -1 in both copies through the twin. Value edits are written in both copies by the row's own thread.
Inserts never happen in place. A structural phase produces an edit list; version 1 applies it by a rebuild at end_phase: keep flags, scan, gather, concatenation with the inserts, stable sort by (row, column, origin), duplicate combination by F2, absorption of the fixed terms when today's condition fixed_terms_absorbable holds (the fixed-term sum of the row summary and one dd_residual per side), transpose by the stable radix sort (467 microseconds + 0.279 ns per nonzero, Stage 0), twins, class plans, fold of the changed rows. Version 2, only if the measured rebuild time is too large on the instances above 1e7 nonzeros: the affected rows and columns are rewritten into free space at the end of the stores (the batch form of today's move_column_to_end) and the full rebuild follows the dead-share rule. Both versions give the same logical state. A rebuild is also made when the dead share exceeds rebuild_dead_fraction or the fixed share rebuild_fixed_fraction, as today, with the dead share now defined as 1 - live entries / stored entries. compact_sparse_lines has no counterpart.

7. RECORDS, OUTPUT, HASH

Records are produced on the device with the key (phase, wave, kind, index) and exist in one order on both executors: ascending index inside a wave, kinds in a fixed order. Pool offsets are an exclusive scan over the batch plus the pool sizes the host passes in. They are flushed to the host stack at every executor switch, when a device buffer is full, and at the end. Inside one wave the records are independent of each other by the conflict rules (a column removed in a wave is not read by another unit of that wave), so the contract of postsolve.hpp:182-183 holds for the order. postsolve() and crush() are unchanged host code.
Output: new row and column numbers by scans over the live flags, gather of the live entries with the column map (rows are already in column order and the map is monotone, so no sort), sides less the fixed-term sums, offset by F3. Standalone: download into memory of the resource (a view, so that no vector is zero-filled first; HISTORY Entry 32 measured that sizing vectors was three quarters of the device path). Inside cuOpt the adapter can take the device arrays.
Hash: a parallel form replaces the chain. Per array, the sum modulo 2^64 of finaliser(position, word) over its elements, then the array sums chained through the finaliser in today's field order. It is an integer reduction, exact on both executors. The chain hash stays available as an option for comparisons with stored results of the sequential engine. The wave hash (tests only) is the same construction over the logical state of 2.1 with entries keyed by (row, column).

9. FIXED COSTS AND THE MODEL OF THE HYBRID RULE

Stage 0, one H200: launch with synchronisation 9.0 microseconds; kernel with an 8-byte read-back 13.8; reduce, scan, compaction up to 1e5 elements 23 to 46; sort of 1e3 to 1e5 elements 94 to 501; a step of 8 launches, one read-back and one compaction 77 to 93; hand-back with an ordered list at most about 141 with a mirror. A fused cascade wave is about two such steps (my estimate, 150 to 200 microseconds); parallel rows about 1 ms plus the sort; an alias batch 2 to 3 ms; a rebuild 1 ms plus 0.6 to 1 ns per nonzero (transpose measured, the rest estimated).
Model (W/hybrid_model.py): every recorded host step of the 240 benchmark instances (one take of a list, or one call of a family that takes once) charged 120 microseconds on the device, a switch of sides 170 microseconds, against the host engine seconds of the same run (Mac). Everything on the device: fixed costs are 131.8% of the host engine seconds below 5e4 nonzeros (93 instances), 83.3% from 5e4 to 2e5 (50), 12.5% from 2e5 to 1e6 (67 instances, 31 of them above 10%), 1.9% from 1e6 to 1e7 (28, none above 10%), 0.2% above 1e7 (2). With the hand-back rule of the hybrid section (down below 20,000 work units in 2 consecutive steps, up from 200,000): 21.4%, 6.7% (17 of 67 above 10%), 1.6%, 0.3% for the four classes from 5e4, and the share of the rule work that runs on the device is 95.1%, 98.2%, 99.8%, 100.0%. The model counts host lists, not snapshot waves (more waves), counts each family as its own step (a fused wave is fewer steps), and sets Mac host seconds against H200 costs; it is an order of magnitude.
Frame for the gain: the whole-matrix parts hold 78.8% of the engine seconds on the 240 benchmark instances and 82.1% on the 30 of at least 1e6 nonzeros (Mac). If those parts ran 10 times faster and the rest stayed at host speed, the engine would be 3.4 and 3.8 times faster. That is arithmetic on measured shares with an assumed factor.

10. WHERE THIS ANGLE BREAKS

1. It replaces a verified engine. State operations, every rule loop, the driver and the hash are new code (roughly 5,000 of the 8,829 lines by my count of the files); numerics, the rule arithmetic, postsolve, io, the oracle and the campaign tool stay. Stored hashes, mutants as patches and tests of state operations are re-based.
2. Small models gain nothing and may lose: the wave engine on seq buffers results and folds rows again. Its time against today's engine is unknown until milestone 2.
3. Chains cost one wave per link. Published figures: 4.4 against 3.1 rounds on average and up to 22 times on one instance (Sofranac et al. section 2.2, 893 instances); 23.53 against 14.54 rounds for delayed application in PaPILO (990 instances). With budgets in work units a long chain can stop earlier than today.
4. In the class from 2e5 to 1e6 nonzeros the fixed costs are of the size of the possible gain on a quarter of the instances (model above).
5. Steps that are sequential inside a line (comparison of a pair of long rows, the prefix test of column stuffing, a class of parallel columns) run on one thread per line; one GPU thread is about 1,000 times slower than a core (cuPSLP section 2.2). Each such step needs a length cap with a parallel form above it, or it is slow on the few very long lines.
6. On x86 above the mirror size nothing can go back to the host except small objects (the edge list of a forest), so every remainder there pays device fixed costs.
7. The whole state must fit the device: about 40 bytes per nonzero plus 28 during a rebuild (from the array list).

11. THE DESIGNED RULES THAT ARE NOT BUILT

They are written directly in wave form, seq first, then cuda, with the conditions of v2_design.txt and lowworth_v2_design.txt as value functions and the conflict rule named per rule in the per-part list. Writing them first in index order would be code that the wave engine replaces. Simple probing (built, in review at edd147a7e) and the singleton-column rules (built) are finished on the sequential engine as they are and serve as the reference for the reductions of their wave forms.

Then the row fold of every row (activities, infinite counts as uint16, largest term, fixed-term sum, counts, extreme coefficients) by the lane-group kernel up to 64 entries and the block kernel above. Flags by fill. Class plans by a stable sort of rows and columns by length class. About 20 launches, 2 radix sorts, 1 read-back. Transfer: 12 bytes per nonzero and the vectors up, nothing down when the presolve stays on the device.
why_host: Below the threshold only. Measured: the device build as a first call lost up to 8.5e5 nonzeros and won from 1.3e6 (15 instances, one H200), but in that measurement three quarters of the device path was the host sizing result vectors, which this design does not have. The model of this round puts the device fixed costs of a whole presolve at 83.3% of the host engine seconds from 5e4 to 2e5 nonzeros (50 of the 240 benchmark instances, Mac seconds) and 12.5% from 2e5 to 1e6. The threshold is fixed by measurement in milestone 9.
same_result_as_today: Transpose, twins and locks: the same arrays as today (bit-equal in 3,734 compared builds, HISTORY Entry 32). Activities: the same bits as today's fold when the start step changes no bound; where it does, today's sums carry two-term updates with a larger update count and the new sums are folds after the start step. Work lists: every row and column in ascending order, as today.
conflict_rule: None between rows or columns. Infeasibility is reported for the smallest index.
expected_gain: The state build is 31.4% of the engine seconds on the 240 benchmark instances (node, 40.4 ns per nonzero) and 34.2% on the 9 testbed instances above 1e7 nonzeros. Device work measured at 0.13 to 0.27 ns per nonzero from 5e6 nonzeros (40 to 48 ms for 2.57e8). With no host arrays to size the part should fall to the upload plus about 1 ms; no integrated run exists.

--- 2
part: Row rules: empty row, infeasible row, redundant row, singleton row, forcing row
runs_on: Device, inside the fused cascade wave; seq for waves below the hand-back threshold on models with a host mirror.
device_algorithm: The fold step gives every flagged row its summary. row_verdicts is a map with one thread per flagged row and O(1) work: the tests of rules_rows.cpp in today's order on the summary (free count, activities with counts and error bound, fixed-term sum, extreme coefficients). A singleton row stores its two bound candidates per row; a forcing row stores the side it meets. The column step of the wave (see bound propagation) reads the verdict of each row of a column: singleton-row candidates and forcing-row fixings enter the same max/min reduction as propagation candidates. apply_row_deletions sets alive to 0 and walks the entries of the deleted rows once to decrement locks and column sizes with integer atomics and to flag new singleton columns. Cost: 2 to 3 launches of the wave.
why_host: Only the tail. Calls below 20,000 work units are 64.9% of all family calls and 0.6% of the engine seconds on the 240 benchmark instances (Mac); 72.8% of the calls take the host less than one fixed device step of 85 microseconds.
same_result_as_today: Not bit for bit. The tests are today's functions, but they read activities folded from scratch (smallest update count, so the error bound is smaller and a test can pass that today waits for a fresh summation) and the state at wave start instead of the state after the previous row. A row that today is deleted as redundant after another row's bound in the same list is deleted one wave later. With exact data the end state of a cascade is expected to be the same; within tolerances it can differ. Records of fixed columns come in ascending column per wave instead of visit order.
conflict_rule: Bounds by max and min per column with the tie to the smaller row index (facts). A column in several forcing rows takes the value of the smallest forcing row index; a forcing row is deleted in the wave only if it set all its free columns, otherwise it is flagged again and is tested in the next wave as a row of constants, with today's tolerance. Lock and size changes are integer atomics.
expected_gain: 5.1% of the engine seconds on the 240 benchmark instances (node); the first call holds 79.8% of its work; lists of at least 10,000 rows hold 92.8% of its work. 62.7% of its units need nothing of the same call and 90.8% are within three levels.

--- 3
part: Bound propagation and the switch to explicit bounds
runs_on: Device, inside the fused cascade wave; seq for the tail as above.
device_algorithm: column_candidates over the binned CSC (lane groups up to 64 entries, one block above, chunks with a second kernel for very long columns, since max and min do not depend on order): per entry in a flagged live row the candidate of implied.hpp on the snapshot activities, residual first, with the guard and the single-infinite-term rule (the entry tests whether its own term is the infinite one); integer candidates moved outward by 4 rounding units. Per column the largest lower and smallest upper candidate with its row. The leader thread of the column applies: integer column by round and compare, fixing when the bounds meet, infeasible index by an integer minimum; continuous column before the switch: the best candidate of the wave becomes the implied record if it beats the valid record by the step; after the switch: the explicit bound, at most 16 waves per bound. For a work list that is small against the columns it touches, the row-driven form gives the same result: candidates of the flagged entries, stable sort by column, reduction by key. mark_frontier flags the rows of changed columns. make_explicit is a map over the columns with a valid record plus mark_frontier. Cost: 3 to 5 launches of the wave; the row-driven form adds a sort (94 to 501 microseconds for 1e3 to 1e5 elements).
why_host: Only the tail. Later lists of a propagation call hold 7.7% of its work and 33.4% of its findings (240 benchmark instances); lists below 100 rows are 1,131 of 2,122 lists with 1.8% of the work. Sofranac et al. section 5 report that a marked sequential code is often faster after single bound changes.
same_result_as_today: Not bit for bit. A wave reads the bounds of its start; today each bound is applied before the next candidate. The bounds reached at an empty work list are the same for exact data; with the guard, the step rule of implied records and the 16 steps they can differ. Which candidate becomes a record is now defined (best of the wave, tie to the smaller row) instead of visit order.
conflict_rule: Max and min per column under a total order, computed inside the column's own thread group; no atomic on a floating-point value. Marks are stores of the constant 1.
expected_gain: 16.4% of the engine seconds on the 240 benchmark instances (node), 23.1% on the testbed below 1e7, 10.1% on the 9 above. The first list of the first call holds 71.0% of its work. Published: 7.4 times over a sequential code on a V100 without transfers (Sofranac et al., 786 instances), with 1.4 times the rounds.

part: Row tightening: integral scaling with the gcd, side rounding, coefficient strengthening
runs_on: Device, inside the fused cascade wave; seq for the tail.
device_algorithm: tighten_rows on flagged rows that the wave did not delete, lane groups up to 64 entries and one block above. Integer rows (free continuous count 0 in the summary): per entry the denominator of the continued fraction of |a| (today's integral_denominator), the least common multiple as an integer reduction with the limit 1000, then today's second pass as reductions (rounded coefficient, drift as a lane sum, gcd). Sides by round_side with the fixed-term sum of the summary. Coefficient strengthening per entry from the snapshot activity. The row's thread group writes values to the CSR and, through the twin, to the CSC, and the sides. Launched after the column step has read the matrix. 2 to 3 launches.
why_host: Only the tail. 85.9% of the tightening calls have no finding and hold 62.5% of its seconds (240 benchmark instances), but those calls are whole-list scans and stay on the device when the list is large.
same_result_as_today: Nearly. A row reads only itself and column bounds, so the order of rows never mattered (97.3% of its units at level 1, the rest is the same row again). Differences: the scale is the least common multiple of per-entry denominators instead of a walk that multiplies as it goes; in exact arithmetic with the limit 1000 both give the same scale (argued, not tested), within the tolerance tol.zero they can differ on single rows; the checks after it are unchanged. Strengthening reads the snapshot activity, which is valid and can be weaker by one wave.
conflict_rule: None: one writer per row. The entries of a column are written by different rows at different positions.
expected_gain: 15.1% of the engine seconds on the 240 benchmark instances (node; 7.7% on the Mac for the same work), 28.5% of the rule work; lists of at least 10,000 rows hold 73.3% of its work.

--- 6
part: Parallel rows: merge of two parallel rows; subtraction of an equation from a row parallel to it up to singleton columns
runs_on: Device when the listed work (entries plus 8 per row) is at least the hand-over threshold or no mirror exists; seq otherwise.
device_algorithm: key_rows: per listed row a line kernel with two reductions, the entry of the smallest core column (min) and the integer sum of the mixes of (column, coefficient scaled by that entry, 20 mantissa bits). Stable radix sort of (hash, core length, row); bucket bounds by adjacent difference, scan and compaction. Leader rounds, at most parallel_bucket_limit: the smallest unclassified row of each bucket (reduction by key) is the leader; each other unclassified row compares itself exactly with it, one thread per pair on the two rows in column order. Merge per class: kept row is the smallest index; its sides are the max of the lower images and the min of the upper images of all rows of the class, each image computed as today; crossing beyond the tolerance is infeasible; removed rows are deleted with integer lock and size updates. Subtraction: per class one pivot equation (fewest singleton columns, then smallest index); each admissible target, after today's size and growth tests as a map, kills its core entries and gets the equation's singleton-column entries as inserts, side shift by the ordered sum. About 25 to 35 launches and library calls plus the sort.
why_host: Small later calls. 63.5% of its calls have no finding; the first call holds 91.5% of its work on the 240 benchmark instances and 95.6% on the 9 above 1e7.
same_result_as_today: Not bit for bit. Today a row is compared with up to 4 unlike neighbours above and below while rows of the bucket are deleted; here with up to 4 leaders. In a bucket with at most 4 classes of mutually parallel rows the same rows are merged; with more classes or with rows that are parallel only within the tolerance the pairs can differ. Sides of a kept row come from one max/min over the class instead of pairwise merges.
conflict_rule: A row belongs to one class; the kept row is written by a reduction over its class; targets write only themselves; the pivot equation is read only. Lock and size decrements are integer atomics (the only conflicts measured under the reservation rule were of this kind). Inserts go to the edit list.
expected_gain: 10.2% of the engine seconds on the 240 benchmark instances, 13.9% on the 9 above 1e7 (12.254 s). On the Mac the keys are 0.576 s of its 0.921 s, the sort and links 0.161 s, comparisons and reductions 0.148 s.

--- 7
part: Doubleton equations and the alias forest (the alias pipeline that simple probing and the single-lock alias share)
runs_on: Device for collection and application. Forest: device from forest_device_min_edges edges (provisional 100,000), seq below, with only the edge list transferred; levels beyond forest_level_cap (64) are finished by seq.
device_algorithm: collect_edges: map over listed rows, compaction in ascending row. Forest: minimum spanning forest with the row index as weight by Boruvka rounds (integer minimum of the outgoing edge per component, hook, pointer jumping on component ids). Rooting: adjacency by a sort, breadth-first levels from the smallest column of each tree, score along tree edges, root by an integer tuple (type, score, live entries, smallest index) as a reduction per tree, levels from the root, composition of the maps level by level from the parent, cut at an inadmissible edge. Apply: bound transfer by max/min per root; fixing of the columns of a root that is fixed; expansion of the entries of all substituted columns by scan and gather into (row, root, origin column, moved value, side product); stable sort; coefficients, side shifts and costs by ordered segment sums with one cancellation test; removed status for substituted columns; alias records in ascending column; inserts to the edit list; cycle rows and cut edges flagged again. About 100 to 150 launches and 5 sorts for a batch with findings (estimate 2 to 3 ms fixed); a call without an edge is one map and one read-back.
why_host: The forest of a small batch: the tree walk and composition are 0.018 s of the 0.317 s of this family on the 240 benchmark instances (Mac), about 37 ns per alias, against at least about 1 ms of launches for a device forest. Deep trees: 72.1% of 485,837 substituted columns are at depth 1, 0.3% beyond 64, the deepest tree has depth 741 on CMS750_4, a model below 5e4 nonzeros.
same_result_as_today: Not bit for bit. Tree edges are the same set as today when the list is ascending, which holds at the first call (94.0% of the work). The root rule and the composition order are today's. Different: all trees are applied in one batch; a root coefficient that several substituted columns feed is one compensated sum in ascending origin column with one cancellation test, where today it is a chain of plain sums with a test after each; sides are shifted once per row instead of once per entry; rows end in column order instead of with the root in the slot of the first substituted entry.
conflict_rule: Roots are not substituted in their batch, so all maps apply together. Writes of several maps into one entry, one side or one cost are ordered segment sums. No row is reserved.
expected_gain: 4.0% of the engine seconds on the 240 benchmark instances, 5.9% on the 9 above 1e7 (neos-4332810-sesia alone 4.346 s for 7,077,830 aliases). On the Mac, row deletion and substitution are 0.250 s of 0.317 s.

======== HYBRID_RULE ========
The rule chooses the executor of each step. It uses only the input size and work counts that the engine has anyway, so it is the same on every machine, and because both executors give the same bits it changes time only.

H0. No device in the build, or executor = seq: everything on seq.
H1. Model size. Input nonzeros below device_min_nnz (provisional 200,000): the whole presolve on seq, nothing is uploaded. Reason: the median host time of a whole presolve is 1.7 ms below 5e4 nonzeros (93 of the 240 benchmark instances) and 15.3 ms from 5e4 to 2e5 (50 instances); in the model of this round the device fixed costs are 131.8% and 83.3% of the host engine seconds in these two classes with everything on the device and still 21.4% from 5e4 to 2e5 with the hand-back rule (Mac seconds, 120 microseconds per recorded step).
H2. Hand-back and hand-over, where a host copy of the state can exist: always on Grace Hopper; on x86 when the state fits mirror_max_bytes (provisional 64 MiB, the placeholder of DESIGN.md 2.1). Work w of the next step = entries of its flagged lines + 8 per line, known from the last read-back. On the device: when w is below handback_work (20,000) in handback_waves (2) consecutive steps, the next steps run on seq. On the host: when w reaches handover_work (200,000), back to the device. The gap between the two values is there so that the engine does not switch back and forth; a switch costs an ordered dirty list each way (at most about 141 microseconds measured with a mirror, about 200 with a gather).
H3. Above the mirror size on x86 there is no hand-back: every step runs on the device. Reason: on the 30 benchmark instances of at least 1e6 nonzeros the calls below one fixed step cost 0.3% of the engine seconds at one step each, and in the model the fixed costs are 1.9% from 1e6 to 1e7 nonzeros without hand-back against 1.6% with it.
H4. Alias forest: seq below forest_device_min_edges (100,000) with only the edge list downloaded and the maps uploaded; levels beyond forest_level_cap (64) are finished on seq.
H5. Memory: when plan_memory(rows, columns, nonzeros) exceeds byte_budget the whole call runs on seq. Falling back to seq after a failed device allocation would read the machine but cannot change a result; whether that is allowed is a question for the owner.
H6. During the build-up, a step without a cuda implementation runs on seq through the sync layer.

Fixed costs against the rule (Stage 0, one H200): launch with synchronisation 9.0 microseconds; kernel with read-back 13.8; reduce, scan, compaction 23 to 46; sort 94 to 501 for 1e3 to 1e5 elements; a step of 8 launches, read-back and compaction 77 to 93; pinned mirror refresh 31 to 184 microseconds below 5e5 nonzeros and 0.86 to 1.84 ms from 3e6 to 1e7; pinned allocation 0.38 s per GB (so the context and its buffers are created by the caller before the timed call). A fused cascade wave is estimated at 150 to 200 microseconds, which is the host time of 15,000 to 20,000 work units at 10 ns; that is where handback_work comes from.

Model of the rule on the recorded host steps of the 240 benchmark instances (W/hybrid_model.py; down 20,000 twice, up 200,000): share of the rule work on the device 95.1% (5e4 to 2e5), 98.2% (2e5 to 1e6), 99.8% (1e6 to 1e7), 100% (above 1e7); fixed costs 6.7% of the host engine seconds from 2e5 to 1e6 (17 of 67 instances above 10%, the worst 24%) and 1.6% from 1e6 to 1e7 (none above 10%).

All five thresholds are fixed once in milestone 9 by the rule of AS-307, applied to the hybrid run against the seq-only run of the same engine: the smallest summed time, ties to the host, and no instance slower than seq only by more than the larger of 5% and 2 ms. They are options, so two runs can differ in them; a run with any other values must give the same hashes, which is itself a test.

======== IDENTITY_RULE ========
Equal, bit for bit, by construction and by test:
1. A run with a GPU and a run without one, for the same settings: the logical state after every wave (bounds, sides, live entries with their values, statuses, records, flags, summaries), the record stack, the reduced model, the statuses, and every statistic that counts work or findings. Seconds are not compared.
2. Runs on different GPU types, on both memory paths (pinned mirror on x86, managed memory on Grace Hopper), with any values of the hybrid thresholds, any sweep form (flags or lists, column-driven or row-driven candidates), any bin boundaries, and any mix of executors (also a mix drawn at random per step in tests).
3. Repeated runs.
The reason is one definition per step whose result does not depend on order (section 1 of the design), and two executors that must agree on every step. So I agree with the preference for the same bits with and without a GPU, and this design gives more than that: the device path equals the host path step by step, so the oracle, the campaign and the wrong engines on the host test the rules of the device path, and a difference between the two is localised to one step of one wave.

Not equal: today's engine and the new one. The reduced model, the record stack and all hashes can differ, because (a) a wave reads the state at its start, (b) activities are always summed from scratch, (c) rows are kept in column order, (d) sums that today run in application order have a fixed order, (e) parallel rows are grouped with leaders, (f) the hash function changes. I disagree with keeping today's bits: reproducing an order of application that was chosen for a sequential loop means index-priority claims, which commit one unit per round on a chain (Blelloch et al. section 5), and incremental activity bits that are history; both work against a device engine and against the rule of one summation order.

What replaces 'equals today': (1) the reductions gate against today's engine, run on the seq executor on the 240 benchmark instances and the 40 testbed instances: geometric mean of today's remaining nonzeros, rows and columns over the new ones at least 0.999 each, every instance below 0.99 in any measure explained, and the gate against the HiGHS reference not below today's values (1.002 on the 240 local dumps, 1.003 on the testbed) by more than 0.001; (2) the oracle, the campaign, the structure and crush checks, the second-presolve test; (3) the wrong engines made again for the wave rules. Today's engine stays selectable (engine = sequential) so that the two can be compared at any time, also at the end over solution quality.

======== DATA_LAYOUT ========
Matrix on the device. CSR: row_start (int64 per row position), row_id and row_pos (int32, position to row and back), col (int32, -1 for a deleted entry), value (double), twin (position of the entry in the CSC; 32-bit while the nonzeros fit 2^31, else 64-bit). CSC: col_start, col_id, col_pos, row (int32), value (double), twin. Rows and columns are stored in class order of their length (six classes up to 64 entries, one class up to 8,192, one above), ascending index inside a class, by a stable sort at every rebuild; entries of a row in ascending column, of a column in ascending row. Values in both copies, as DESIGN.md 2.3 asks. Liveness of an entry = row alive and column not removed and index not -1; a deleted row or removed column writes no entry.

Bytes (from the array list, not measured): 32 per nonzero with 32-bit positions, 40 with 64-bit; rebuild scratch about 28 per nonzero (keys and positions with a second buffer); peak about 60 to 68 per nonzero. Per row about 110 bytes: sides 16, alive 1, version 4, flags 2, summary (activities 2 x (hi 8, lo 8, largest term 8, infinite count 2), fixed-term sum 24, counts 8, three extreme coefficients 24, single free position 4), verdict and candidate scratch about 24, singleton count 4, key 12. Per column about 120 bytes: bounds 16, cost 8, type and status 2, locks 8, size 4, implied records 32, step counters 2, offset contribution 16, candidate scratch 24, flags 2, growth factor 8. For 2.57e8 nonzeros (the largest testbed instance) that is about 10 GB resident and 17 GB at the peak of a rebuild.

Activities. Never updated. A row is flagged activity-dirty when an entry of it or a bound of one of its columns changes; the fold step recomputes its summary before any step reads it. Order of the sum: the live entries of the row in storage order (ascending column), entry k to lane k mod activity_lanes(n), dd_add_product inside a lane, lanes merged by the tree of numerics.hpp:145-161; an infinite term enters as a * 0 and is counted. Infinite counts are two uint16_t arrays; a count that saturates marks the side unusable until the next fold. The position of a single infinite entry is not stored: the candidate step tests whether its own term is the infinite one.

Deletions. Rows by the alive flag, columns by status, entries by index -1 through the twin. No compaction between rebuilds. Rebuild when inserts are pending at the end of a phase, when 1 - live entries / stored entries exceeds rebuild_dead_fraction, or when the fixed share exceeds rebuild_fixed_fraction and the fixed terms are absorbable.

Work lists. One uint16 mask per row and per column (the 11 row consumers and 5 column consumers of today). A step visits the flagged indices in ascending order, either by testing the flag in a kernel over all lines (wide lists) or over a list made by an order-preserving select (narrow lists); the two forms give the same result. Marks are stores of a constant.

Records. Device buffers per record kind plus the pool of saved entries; each finding stamped with (wave, index); ordered select per call; flushed to the host stack at every executor switch, when a buffer is full and at the end.

On the host. Always: options, budgets, statistics, the wave statuses, the record stack after each flush. x86 with a discrete GPU, state up to mirror_max_bytes: a pageable or pinned mirror of the row and column arrays, brought current by dirty records in ascending index (column record: index, bounds, cost, status, type; row record: index, sides, alive, version) or by whole arrays above a share of dirty lines; the matrix is downloaded when a seq step needs it and it changed since the last download (after a rebuild the whole matrix, after value edits the values of the dirty rows). The same lists go back before the next device step. One side owns the state at a time. x86 above mirror_max_bytes: no mirror; only small objects cross (wave status, forest edges and maps, records, the reduced model). Grace Hopper: all arrays in one managed slab, 2 MiB aligned, preferred location device, accessed-by host; cudaMalloc memory is not used for anything the host must read; host_access waits for the stream and returns the array itself, release prefetches the range; no mirror, no copy, one copy of the matrix for both executors. That path is functional only until a GH200 node is measured, and is tested on x86 by forcing managed memory on small models. Host-only build: the same handles on host memory, rows in index order; the layout is not part of the logical state.

Slab sizes come from plan_memory(rows, columns, nonzeros, options), a function of the input sizes; nothing is allocated during a presolve; the temporary storage of CCCL calls is passed in from a scratch slab.

======== VERIFICATION ========
1. Value functions (the arithmetic of every rule, shared by both executors). Host: today's rule tests are kept on them, and the extraction is neutral, shown by unchanged hashes of the sequential engine on the 240 benchmark instances, the 40 testbed instances and a fixed list of campaign seeds. Device: every function gives the host's bits on random and special inputs (both zeros, subnormals, the 1e20 boundary, 2^54, cancellation); this also settles whether nvcc compiles the shared headers.

2. Step equality. For every step, the cuda executor and the seq executor run on the same input state and every output array is compared bit for bit: on states recorded from campaign models, from generated models that cover every length class (0 to 70, 255 to 258, 513, 8,191 to 8,193, 20,000 entries) and from the benchmark instances. Models carry integer column types wherever a step rounds. This is the test 'the device equals the host', taken step by step.

3. Wave-hash sequences. With phase hashes on, the hash of the logical state and of the record stack after every wave is equal for: all seq, all cuda, the default hybrid, a mix of executors drawn from the seed, both sweep forms, both candidate forms, forced bin boundaries (0, 2, 64), both rebuild versions, both memory paths. Run on campaign models and on the 240 and the 40 with the structure check and the crush check through the MIPLIB solution files.

4. Semantics of the wave engine, on the seq executor, on the Mac and the node: the oracle (optimum of random small MIPs by enumeration), the structure check, the crush check of the records, the second-presolve test, in the release and the assertion build; a campaign of the same size as for the sequential engine before the wave engine becomes the default, and a billion models before acceptance. Assertion builds recompute every derived array (summaries, locks, sizes, singleton counts) from scratch after every wave and compare.

5. Wrong engines. The 99 mutants are made again for the wave engine in three groups: wrong rule (in the value-function headers, one mutant covers both executors and must be caught by a named oracle or check test); wrong seq step (conflict rule dropped, tie rule reversed, a flag not set, a record out of order); wrong kernel, built only on the node (lane dealing, merge offsets, a library reduction for a sum, count capped at 1, lo not loaded, a frontier test dropped), each of which must fail step equality. A check counts only after it failed on its wrong engine.

6. Against today's engine: remaining rows, columns and nonzeros per instance on the 240 and the 40, statuses, the number of calls that stop on a budget or report limited, and the list of instances that differ with the cause.

7. Determinism: three repeated runs with equal wave-hash sequences on the 240 and the 40; a second GPU type as a cluster job; Grace Hopper when a node is used; managed memory forced on x86 for models up to 1e6 nonzeros.

8. New in the campaign tool (G/tools/gprs_fuzz.cpp): --engine sequential|wave; --executor seq|cuda|mixed with the mix drawn from a draw of its own so that existing cases keep their seeds; the hybrid thresholds, sweep forms and bin boundaries as drawn settings; the wave-hash sequence as an output that two runs can be compared on; a device campaign target (gprs_fuzz_device) that compares every wave with seq in the assertion build. A device campaign is expected to cost about a millisecond per model (estimate of the Stage 1b design), so it runs millions, not billions; the volume is on seq, which has the same bits.

9. Kernel variants are benchmarked against the current kernel before they replace it (gprs_device_bench on recorded states), as the review of cuOpt PR 2372 asks.

10. Overheads in every run: upload, download, each sync, rebuilds, record flushes, output, hash, context creation (cold start apart), next to the per-family figures; overheads.csv gets these columns.

======== ACCEPTANCE ========
The GPU acceleration of Stage 1 is complete when all of the following hold. Figures marked 'proposed' are targets for the owner to set; they come from the measured shares, not from a device run.

1. Classification. Every step of every part is listed with its executor. A step that runs on seq when the device is used has a measured reason from one of these classes: model below device_min_nnz, work below the hand-back threshold with a host copy available, forest below the edge threshold or beyond the level cap, driver, record stack. No step is on seq because its cuda form is missing.
2. Identity. Wave-hash sequences are equal between all seq, all cuda, the default hybrid and a random mix, across three repeated runs, on a second GPU type and on both memory paths, on the 240 benchmark instances, the 40 testbed instances, a billion campaign models on seq and at least ten million through the device.
3. Share of work on the device, in the engine's own work units, reported per size class of the 240 and the testbed. Proposed: at least 95% from 1e6 nonzeros and at least 80% from device_min_nnz to 1e6 (the model of this round gives 99.8% and 98.2% for the rule work).
4. Time of the hybrid against the seq-only run of the same engine, minimum of three alternating runs: no instance slower by more than the larger of 5% and 2 ms.
5. Time against today's engine (commit 04692babd, node ipp2-0043). Proposed: the 9 testbed instances above 1e7 nonzeros in at most a quarter of today's 87.8 s; the benchmark instances from 1e6 to 1e7 nonzeros in at most a third of today's time; from device_min_nnz to 1e6 not slower in the sum; below device_min_nnz the wave engine on seq at most 1.1 times today's sum, and the HiGHS time rule met on every instance from 50,000 nonzeros.
6. Reductions. The gate of the identity rule against today's engine, and the Stage 1c gate against HiGHS for the full rule set.
7. Checks. Oracle, structure and crush checks clean; every wrong engine and every wrong kernel caught by a named check; no wrong status on the 240 and the 40.
8. Overheads (upload, download, syncs, rebuilds, record flushes, output, hash, context) are in every stored run.
9. Every new assumption of this plan has an entry in ASSUMPTIONS.md with its switch: engine (sequential or wave), executor, the five hybrid thresholds, fused cascade, the leader limit of parallel rows, the scale search by least common multiple, the forest rule, the claim priority of each rule that uses claims, the order of long-row sums, hash kind, rebuild version, memory path.
Under the narrow reading of 'stage 1' (the built rule set), criteria 1 to 9 at the end of milestone 9 are the acceptance; under the wide reading, the same criteria at the end of milestone 10.

======== REDUCTIONS_LOST ========
Nothing of this design is built, so no loss or gain is measured. The design does not reproduce today's reduced model. Where it can differ, the direction I expect, and how it is measured (all on the seq executor at milestones 1 and 2, per instance on the 240 benchmark instances and the 40 testbed instances, in rows, columns and nonzeros):

1. Budgets on chains (possible loss). A wave reads the state of its start, so a chain costs one wave per link and each wave charges its work. A call can then stop on its budget where today it finishes. Today 20 calls stop on a budget on the 240 (tightening 16, propagation 2, doubleton 2) and 6 instances end without a fixed point; the longest chains are 834 (neos-1122047), 197 (lotsize), 183 (irish-electricity), 141 (unitcal_7). Measured by the count of stopped and limited calls and of fixed points next to today's, and by the reductions of those instances. Remedy without a rule change: the passes of the budget, which are options.
2. The only outside figure for snapshot against immediate application: PaPILO on one thread leaves 56,803 against 56,258 nonzeros (1.0% more) with delayed application, at 23.53 against 14.54 rounds (990 instances, read through the fetch tool by the research step). PaPILO limits its rounds; this engine runs to an empty work list on 234 of 240 instances, so I expect less than that, without proof.
3. Parallel rows (loss or gain on single instances). Up to 4 leaders per bucket instead of 4 unlike neighbours on each side. Differs only in buckets with more than 4 classes or with rows parallel within the tolerance only. Measured by merges and subtractions per instance against today's 351,049 and 8,916 on the 240.
4. Implied-bound records (either way). The record of a continuous column is the best candidate of a wave instead of the first in visit order; the free singleton test reads these. Measured by the count of free singleton columns against today's 13,217 and 2,685.
5. Activities from scratch (possible gain). The guard reads the smallest update count a row can have, so fewer candidates and tests are dropped than with updated sums. Size unknown.
6. Sums with a fixed order and one cancellation test (either way, single entries). A root coefficient that cancels in a partial sum today but not in the full sum, or the reverse.
7. Scale search by least common multiple (either way, single rows within tol.zero).
8. All alias trees in one batch and simple probing without the refusal of rows in list order (possible gain in rounds, same end state expected).
9. The singleton-column history rules in ascending row order of a wave instead of list order (either way where saved_row_factor or the growth limit binds; today growth_refused and saved_row_refused count these).

If the gate fails on a part, that part has a switch back to a form closer to today's (for example leaders against neighbours for the parallel rows), and engine = sequential stays available. If the owner requires that nothing may differ from today's reduced model, this design is the wrong one and a design that reproduces the host order is needed.

======== RISKS ========
- The reductions gate against today's engine fails or needs many explanations: the wave order, the leaders and the budgets all move single instances. The gate comes early (milestones 1 and 2, on the host) so that this is known before any kernel is written.
- The wave engine on seq is slower than today's engine on small and mid-size models (buffered results, a second fold per row and wave, more waves). Then either two engines are kept, split by model size, which doubles the rule code, or small models get slower. Unknown until milestone 2.
- Chains: one wave per link. Published increases are 1.4 times on average and 22 times at worst; the fixed cost of a wave (estimated 150 to 200 microseconds) makes a chain of narrow waves expensive on the device, and the hand-back that avoids it exists only where a host copy exists.
- From 2e5 to 1e6 nonzeros the modelled fixed costs are 6.7% of the host engine seconds in the sum and above 10% on 17 of 67 benchmark instances; the device may not pay there, and device_min_nnz may end near 1e6.
- The size of the rewrite: state operations, rule loops, driver and hash are new; the 99 wrong engines and part of the 473 tests are made again; the engine at 1.002 of the HiGHS reference has to be reached again.
- The validity of simultaneous application for the dual rules (dual bound strengthening, dominated column, parallel-column dominance, implied equation) rests on arguments of this text. The Stage 1c reviews broke several sequential guards by counterexample; the wave forms need the same review before they are built.
- Step equality rests on IEEE behaviour of + - * / fma ceil floor with contraction off, on nvcc accepting the shared headers, and on stable radix sort and order-preserving select in CCCL. A compiler or CCCL upgrade needs the equality tests rerun; a second GPU type has never been measured.
- Steps that are sequential inside a line (pair comparison of long rows, the prefix test of stuffing, a class of parallel columns, an ordered sum with very many terms) run on one GPU thread, about 1,000 times slower than a core; each needs a cap and a parallel form above it.
- A rebuild after every structural phase with inserts costs a pass over the matrix (about 0.1 s at 2.57e8 nonzeros by the measured transpose alone); with several such phases per round the instances above 1e7 nonzeros may need the rewrite of affected lines, which is the most intricate storage code of the design.
- Device memory: about 40 bytes per nonzero resident and up to 68 at the peak of a rebuild; the largest instances need about 17 GB and do not fit next to other users of a small GPU.
- The sync layer is the place where a missed dirty record gives a wrong result, not a slow one. Guards: assertion builds compare the two copies after every sync; the campaign runs with executors mixed at random.
- Shared value functions mean a wrong rule is wrong in both executors and equality does not show it; the independent checks are the oracle, the campaign, the mutants and the comparison with today's engine.
- The campaign speed of 760,000 models per second is of today's engine; the wave engine on seq may be slower per tiny model, which makes a billion models cost more node time.
- Grace Hopper is functional only until it is measured; the thresholds tuned on x86 may be wrong there, although they cannot change a result.
- Pausing the remaining Stage 1c rules delays the gate against HiGHS with all cheap rules until milestone 10.

======== OPEN_FOR_OWNER ========
- The central decision: may the engine's order of application change, so that the reduced model and all hashes differ from today's engine, with the reductions gate (0.999 in the geometric mean of nonzeros, rows and columns against today's, every instance below 0.99 explained) in place of bit equality with today? If not, this design is not the one to take.
- The remaining Stage 1c rules (parallel-column dominance and merge, dual bound strengthening, single-lock alias and the five further rules): write them once in wave form after the wave engine exists (my proposal), or finish them on the sequential engine first and write them a second time.
- Simple probing (built, in review at edd147a7e): finish its review on the sequential engine so that it is a reference for its wave form (my proposal), or leave it.
- After the gate of milestone 2: is today's sequential engine retired, kept only as a switch for comparisons, or kept as the engine for models below a size if the wave engine on seq turns out slower there?
- The hash: the parallel form replaces the chain hash and with it every stored hash. Agreed?
- Rows above 8,192 entries: keep the summation order of numerics.hpp (one block per row, slow on very long rows), or change it now to chunks of 8,192 entries, since all hashes change anyway? The Stage 1b design put the same question with a higher price.
