======== SUMMARY ========
Inventory of Stage 1 of the gprs host engine for a device design, made from the code (8,829 lines read in full, plus simple probing at commit edd147a7e), the stored runs (240 benchmark instances, testbed 31 and 9) and the existing device code and designs. Read-only; nothing was built or run except two aggregation scripts over stored JSON. Main findings: (1) every state change goes through 16 state operations that keep stores, twins, sizes, activities, locks, versions and 16 work lists consistent; all derived arrays are recomputable by maps, sorts and reductions, but the host's incrementally updated activities (bits, update counts, largest term) and its list orders are history and are hashed. (2) By shape: row tightening, dual fixing, the start step, the tests of the row rules, the key step of parallel rows and the collection step of doubleton/simple probing are independent maps; parallel rows are a sort plus short chains inside buckets; propagation, row rules and the singleton-column family are cascades bounded only by budgets; alias application conflicts on rows shared by several substituted columns. (3) Today's shares (240 instances, 19.47 s): state build 31.4%, propagation 16.4%, tightening 15.1%, parallel rows 10.2%, hash 5.5%, row rules 5.1%, storage 5.1%, output 4.6%, doubleton 4.0%, singleton columns 1.3%, dual fixing 0.6%. The first propagation call holds 74% of propagation work on the 240 (65% on both testbed sets), not the 92.5% of the earlier measurement. (4) Order-dependent floating-point results beyond activities exist: the objective offset, cost sums and root coefficients in substitutions, repeated side shifts, and the row storage order after move_entry. (5) model_hash is a serial chain by definition; state_hash covers layout, list order and activity counters. (6) Device code that exists: the bit-equal state build (CSC, twins, locks; not integrated, no activity fold); Stage 0 sweep kernels; the Stage 1b propagation design (nothing built); no device form exists for any other rule.

Finding 1. Sizes, row_free_size, row_singletons, locks, the counters and the activities are all functions of the stores, the sides, the bounds and the status flags, so a device engine can recompute them by maps and reductions in place of the host's incremental updates. Three things are not such functions: the bits of an incrementally updated activity with its updates and max_term (they depend on every term the sum ever held), row_version (a count of edits) and the order of the lists.
