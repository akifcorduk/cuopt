Judgement of the three designs.
- validity_first is the base. It keeps every binding constraint, changes no host bit (numerics.hpp order, state_hash), gets every state invariant by construction (the host applies device results through tighten_lower / tighten_upper), and defines the device round once in plain C++ so that the oracle and the campaign test it without a GPU. Its weak points: the first GPU round comes only in its fourth milestone, its hand-over compares every row and column per call, and any coefficient change forces a new upload of the matrix.
- smallest_first has the same architecture. Grafted from it: the milestone order (an end-to-end round first), class boundaries as settings so that the block and chunk kernels run on oracle-size models, a block kernel whose lane count comes from the row length, slabs sized by a pure function of the input and no rmm class or global resource, an event journal in state_t that no hash covers, coefficient changes written in place, the shadow log for the threshold measurements. Not taken: the device deciding implied-bound records itself (it needs six more mirrored arrays and the row versions; the host decides at the hand-back instead), and a CSC without values (DESIGN.md 2.3 asks for values in both).
- performance_first is the best on cost. Grafted from it: the per-column decision as one shared function on values, the insight that an executor that equals the reference bit for bit can be replaced without changing a result, the threshold condition 'no instance slower than host only', and its cost ideas as measured variants (round stamps instead of cleared marks, lists claimed inside kernels, a gate word per row, a row-driven candidate step by sort). Rejected as baseline: (a) the chunk rule for rows above 8,192 entries, which changes numerics.hpp and the stored host hashes before any benchmark, against the rule that a variant is benchmarked before it replaces another; (b) writing device sums into the host accumulators through two new state operations that repeat fix_col's bookkeeping and need exact counts and slot sums; (c) three device lists inside frontier_set_t that enter state_hash when tracking is on, so the host hash would depend on whether a device engine is attached; (d) lists whose order depends on thread timing in the first version.
Nothing in the result needs cuOpt, and every path can be forced on tiny models.

The design in ten sentences.
1. The host state_t stays the only authority; the device engine is a second way to carry out the first part of the propagation call of a cascade pass, and the host rule finishes what is left.
2. A device call takes the propagation list and returns an ordered list of bound changes of integer columns, one implied-bound candidate per continuous column and side, the rows still pending and an outcome; the host applies them in ascending column index through tighten_lower, tighten_upper and record_implied_*.
3. The device never updates an activity; every activity it uses is summed from scratch in the order of numerics.hpp:139-155, so a device candidate is, bit for bit, what the host function candidate() returns on a row it has just recomputed.
4. The round is defined once in plain C++ (reference backend in the host library); the CUDA backend must return the same bits round by round, which is the test 'a GPU batch equals its sequential replay'.
5. Two sweeps as in cuOpt's load-balanced code: rows are folded over the binned CSR, candidates are reduced per column over the binned CSC by max and min; no floating-point atomic and no library reduction of a sum.
6. Rows up to 64 entries use the Stage 0 lane-group kernel; longer rows one 256-thread block with a hand-written tree, also above 8,192 entries, so numerics.hpp and the stored hashes do not change; a chunk rule for both engines is measured in milestone 3 and is your decision.
7. The device matrix is a binned copy of the live host matrix with one definition (make_device_image); however it is produced (upload, build on the device, compaction, value writes), it must equal that function of the host state, array for array.
8. Settings are split into those that can change a result (engine switch, minimum size, frontier work, hand-back rule, fixed-cost budget, byte budget) and those that cannot (sweep form, class boundaries, memory path, how the matrix and the mirrors are brought up to date); only the first group has to be fixed by measurement.
9. Memory comes from one presolve-owned resource with host_access and release: device memory with pinned staging and dirty lists on x86, managed memory written and read in place on Grace Hopper, the same engine code above it.
10. Seven milestones, each ending with passing tests: a device round end to end in the host driver (reference backend on the Mac, a thin CUDA backend on the node); all length classes and real instances; frontier forms in lane-group order; rebuild on the device; hand-over proportional to the changes on both memory paths; measurements; fixed thresholds and gates.

Expectation, stated plainly. Bound propagation is about 7% of the host engine's time in the stored results (reader's figure), the first and largest call stays on the host by the plan, and a rounds-from-one-snapshot engine needs one round per link of an implication chain. Stage 1b is not expected to move the Stage 1 time gate; its value is the tested engine, the hand-over and the measured thresholds for Stage 2. The device stays off by default until milestone 7.

C. Ownership and hand-over.
- The host owns matrix, bounds, activities, lists, counters and records at all times. The device holds a derived copy of the matrix and of bounds, sides and flags; its activities and the bounds it changes during a call are scratch of that call.
- Hand-over to the device, at the start of run(): the protocol compares the counters it stored at the last hand-over. No image yet, or coefficient_changes moved (from milestone 5: an entry was added, deleted or moved): the image is derived again. A rebuild was noted: mirrors whole, then compaction on the device (milestone 4) or a new image. bound_changes or live_cols moved: column mirrors. side_changes or live_rows moved: row mirrors. Milestones 1 to 4 send whole arrays; from milestone 5 records of the journalled rows and columns and the values of rows whose coefficients changed. In assertion builds image and mirrors are downloaded after every hand-over and compared with make_device_image(st) and the host arrays, and every alive row is folded by the backend and compared bit for bit with state_t::fold_row_activity.
- Hand-back, at the end of the device rounds: the three result lists; the host replays them (round protocol). Columns changed by the replay are sent again with the next hand-over like any other host change, so the device copy always follows the host and no rule about the sign of a zero is needed.
- Infeasible outcome: no hand-back; the state is not used again (rules.hpp:65-66).
- Failure. A need above byte_budget or 2^31 - 1 free nonzeros makes the device not eligible, from the model and the settings alone. A failed allocation or CUDA error is a hard error (DESIGN.md section 8: FAILED is an assertion in the standalone project). Because the host state is untouched until the replay and the reference backend returns the same result, a product fallback at Stage 5 can redo the call on the reference backend without changing a result.
- The device context (stream, slabs, pinned staging) is created once by the caller before the timed call and outlives presolve calls.

===== DATA_LAYOUT =====
1. Device matrix (the image). One definition, used by make_device_image, by the reference backend and on the device, and compared array for array in tests.
- Row i of the image is the list of live entries of host row i in host storage order, entries of fixed columns included, tombstones skipped. Its length is csr.size[i], so activity_lanes and the lane of every entry are those of state_t::fold_row_activity (state_build.cpp:176-209). The host state is not rebuilt before the image is taken. A dead row is not in the image.
- Rows are stored in class order: class 0 up to 2 entries, 1 for 3-4, 2 for 5-8, 3 for 9-16, 4 for 17-32, 5 for 33-64, 6 for 65 to 8,192, 7 above; ascending host row index inside a class (a stable sort, so there is one copy and no order that depends on timing). Arrays: row_start (int64, by position, rows + 1), row_id (int32, position to host row), row_pos (int32, host row to position), row_len (int32, by host row), csr_col (int32, host column index), csr_val (double).
- Columns are stored in class order of their length in the image (six classes up to 64 entries, one block up to col_chunk, chunks above), ascending host column index inside a class; the entries of a column are in the order of their CSR position, which a stable sort on the column gives. Arrays: col_start (int64), col_id (int32), csc_row (int32, host row index), csc_val (double); chunk tables for long columns as chunk_view_t in sweeps.cu. Values are in both orientations as DESIGN.md 2.3 asks; there are no twins. A value written later finds its CSC entry by a search over the column, whose rows are ascending in row_pos.
- 64-bit offsets and 32-bit ids. Entry positions inside build and compaction are 32 bit.
- Class plans (first position, first warp and count per class) are computed on the host from lengths it knows, so a build needs no read-back.
- After a build the host can delete rows and fix columns. Such rows stay in the image as dead rows (row_alive 0) until a compaction; a fixed column keeps its entries as constant terms, as on the host. A host rebuild drops the entries of fixed columns and shifts sides, so after it the image must be compacted or derived again before the next round.

2. Mutable state on the device, indexed by host row or column index, so that records and lists need no translation (a state in class order is a measured variant).
- col_bound (bound_t pairs: one 16-byte load per entry in the fold, as sweeps.cu:320-325 does), col_flag (uint8: integer, live, has entries in the image).
- row_side (bound_t), row_alive (uint8).
- Activities, two sides, split arrays as the owner's rule asks, scratch of a round and never handed to the host: act_hi[2] (double), act_lo[2] (double, its own array), act_inf[2] (uint16_t count of infinite terms, saturating at inf_count_cap), act_maxterm[2] (double). No paired value and no flag bit inside the count. The count only has to tell 0, 1 and more, because the device never decrements it and never hands it over; a saturated count gives no candidate until the next fold, which is the plan's 'skipped until recounted'. The number of finite terms is row_len minus the count. The position of the single infinite entry is not stored on the device: the candidate kernel runs over columns and tests whether its own term is the infinite one (as sweeps.cu:505-507); the host keeps inf_slot. lo is always loaded, because a fold result is not normalised (state.hpp:84-85); loading it on a flag is a measured variant with equal bits.
- Marks (uint8, written only with the constant 1, cleared by cudaMemsetAsync): row_front, row_next (swapped after a round), col_cand (list form), col_changed and col_impl (per call).
- Implied candidates of the call per continuous column: impl_lower, impl_upper (double), impl_lower_row, impl_upper_row (int32).
- round_status_t in device memory, zeroed before a round, written by integer atomics once per block, read back once per round through pinned memory.

3. Hand-over structures.
- To the device: the frontier as a list of host rows. Milestones 1 to 4: the four mirror arrays whole when a counter says they changed. From milestone 5, records in the order of the first event, each index once so that the scatter has no race: column record {int32 col; uint8 flag; double lower, upper}, row record {int32 row; uint8 alive; double lower, upper}, and for a row whose coefficients changed its values in storage order. Whole arrays are sent instead when more than sync_list_share of the lines changed.
- From the device: round_status_t per round; at the end the three lists of device_result_t in ascending host index.
- device_journal_t in state_t (milestone 5): a mark byte per row (sides or liveness changed; values changed; entries added, deleted or moved) and per column, two lists in first-event order, counters of events, a flag for rebuild. Filled only while a device engine is attached; not hashed; read by no rule.
- The pinned mirror of the matrix below 64 MiB and the gather above it (DESIGN.md 2.1 and 2.2) do not occur in Stage 1b: every Stage 1 rule edits the host state, so state_t's arrays are the host copy at every size. That threshold stays a placeholder for the overlay design of Stage 2.

4. Memory resource (G/device/src/memory_resource.hpp), owned by the device context.
- plan_memory(nrows, ncols, nnz, options) is a pure function of the input sizes and gives the slab sizes: matrix, state, scratch (temporary storage of CCCL calls, always passed in by the caller, and build scratch) and staging. The slabs are made once; make_array<T>(slab, n) takes from a slab; nothing is allocated during a presolve. host_access(array, first, n, mode) and release(...) are the pair of DESIGN.md 2.2.
- x86 with a discrete GPU (pinned path): slabs from cudaMalloc, one pinned staging slab (64 MiB by default, used as a window so that a large upload is streamed). host_access for writing returns a block of the staging slab and release copies it to the device, as a whole range or as records that a scatter kernel writes; host_access for reading copies device to staging and waits. This is the x86 form of the owner's constraint: dirty lists in a fixed order through pinned buffers.
- Grace Hopper (managed path): the same arrays in one managed slab, aligned to 2 MiB, preferred location device, accessed-by host. host_access waits for the stream and returns the array's own address, so the host writes image, mirrors and records in place and reads results in place; release prefetches the range to the device. No staging and no copy. Selected by the device attribute for direct managed-memory access from the host (name from memory: cudaDevAttrDirectManagedMemAccessFromHost) or forced by memory_path; forced on x86 it works through page faults, which is how it is tested until a GH200 node exists. No time or memory figure is claimed for it.
- All engine code above host_access and release is the same on both paths, so the memory path cannot change a result.
- On both paths the host matrix stays in state_t's std::vector storage in Stage 1b. One copy read in place by both engines needs state_t's arrays inside the resource; that is a decision for the owner.

5. Bytes (from the array list, not measured): image 24 bytes per nonzero plus about 16 per row and column; state about 75 bytes per row and 45 per column; build scratch on the device at most about 28 bytes per nonzero (uploaded CSR 12, sort keys and positions with a second buffer 16). Peak about 52 bytes per nonzero against about 110 in the Stage 0 benchmark.

===== KERNELS =====
All kernels run on the one stream of the context, in 256-thread blocks unless said otherwise. Arithmetic comes only from numerics.hpp and propagation_rule.hpp. 'From' names the Stage 0 code in G/microbench/sweeps.cu that is the starting point; I compared its arithmetic with the host functions line by line (sweeps.cu:200-224 against numerics.hpp:42-93).

1. fold_light_kernel, from act_light_kernel (sweeps.cu:346-386, split layout, atomic count, compensated).
Inputs: binned CSR, col_bound, a class plan, an optional list of positions, row_id, row_alive, row_front. Outputs, by host row index: act_hi, act_lo, act_inf, act_maxterm of both sides; in list form also col_cand marks for the columns of the entries read.
Scheduling: a row of class c (0 to 5) is folded by 2^c adjacent lanes of a warp, 32 >> c rows per warp, one launch for all light classes. Lane s reads the entries at ranks s and s + 2^c.
Order: each lane starts at (+0, +0) and adds with dd_add_product in storage order; a term that is_infinite_term is counted and not added, which leaves the lane as the host's a * 0 does, bit for bit (state_build.cpp:67-97); lanes are merged by __shfl_down_sync with offsets 2^c / 2 down to 1 and dd_add(own, partner). That is the tree of numerics.hpp:139-143. max_term goes through the same shuffles as a maximum. Count: local in the scan, one atomicAdd on a shared-memory integer per side only when the local count is not zero, between two __syncwarp calls; class 0 needs none; the lane with s = 0 stores min(count, inf_count_cap). No extra reduction for the counts.
Forms: all rows with a test of row_alive and row_front, where lanes of a skipped row scan nothing but take part in every shuffle; or a list with a plan from its per-class counts. Both run the same lanes on the same entries.
Fallback of decision 5 with equal bits: fold_light_serial_kernel, one thread per row that computes the lanes one after the other and merges them as fold_light_row does (state_build.cpp:132-173).

2. fold_block_kernel, replacing block_fold (sweeps.cu:388-414).
One block per row above row_light_max entries. lanes = activity_lanes(row_len); thread t below lanes adds the entries at ranks t, t + lanes, ... in order; every thread writes its two (hi, lo) pairs to shared memory; for off = lanes / 2 down to 32 the threads below off set lane[t] = dd_add(lane[t], lane[t + off]) with one __syncthreads per level; offsets 16 to 1 are shuffles in warp 0. Lanes without an entry hold (+0, +0) and change no bit, which is why the host skips them (state_build.cpp:115-124). cub::BlockReduce is not used for a sum. Counts by the integer atomic on block-shared integers, no second reduction; max_term by a block maximum. Because the lane count comes from the row length, this kernel gives the bits of kernel 1 for a short row, so tests send every row through it (row_light_max = 0). Rows from row_long_min entries use the same kernel in a launch of their own; the order of numerics.hpp is kept, at a latency of row length / 256 entries per thread. The chunk kernels for rows (sweeps.cu:433-469) are not taken: the running compensated sum of a lane cannot be cut. A chunk rule for both engines is a bench-only kernel in milestone 3.

3. Candidate kernels: cand_light_kernel (from sweeps.cu:568-590), cand_block_kernel (601-622), cand_chunk_kernel and cand_chunk_finalize_kernel (624-647), cand_chunk_mark_kernel.
Inputs: binned CSC, col_id, col_bound, col_flag, row_side, row_alive, row_front, row_len, the activity arrays, tolerances; a plan and optionally a list of columns. Outputs: col_bound and col_flag of the own column, col_changed, row_next for the alive rows of a changed column, the implied candidates of continuous columns, the counters of the round.
A group or block reads its column's bounds and flag once; a column that is not live does nothing. Per entry in an alive row with row_front set: entry_candidates of propagation_rule.hpp, with the loads in the host's order: side, count, then hi, lo, max_term and length. The upper side uses the minimum activity, the lower side the maximum. Integer column: the candidate is moved outward. Every candidate is carried as (value, row).
Reduction: largest lower and smallest upper pair over the lanes by shuffles (light), over the block (cub::BlockReduce with the pair comparison, a min/max reduction, which DESIGN.md 2.5 allows), per chunk and then over the chunks (above col_chunk; chunks are allowed here because the result does not depend on the order). The pair comparison is a total order, so any tree gives the same pair.
Apply, by lane 0 or thread 0 of the column only. Integer column: decide_integer_bounds on the column's own bounds; infeasible lowers the smallest infeasible column index by an integer atomicMin; a change writes col_bound, clears the live bit when the bounds meet and sets col_changed. Continuous column: the explicit bounds are not written; the pair replaces the stored candidate of the call when it is better (larger lower or smaller upper; equal values to the smaller row), and col_impl is set.
Mark: the leader tells its group whether the column changed; each lane or thread walks its entries again and stores 1 into row_next for alive rows (long columns: a third launch over the chunks of changed columns).
Counters: candidate columns (live columns with an entry in an alive frontier row) and their entries in alive rows, changed columns and their entries in alive rows, summed per block in shared memory and added with one integer atomic per block.
Why there is no race and no dependence on timing: a column's bounds are read and written only by its own group, the read first; activities, sides and frontier marks are read-only here; marks are stores of one value; everything shared between columns is an integer atomic. Column scheduling (lane groups, one thread per column, block sizes, chunk length) can change no result, so it is free to depend on the size.

4. Frontier kernels: mark_rows_kernel (row_front from the uploaded list of host rows); frontier_stats_kernel (rows and summed lengths of the marked alive rows per class, by integer block sums); for the list form an order-preserving select of the marked positions (cub::DeviceSelect::Flagged over the positions; that it keeps the order is from memory and is tested) whose class boundaries are the prefix sums of the per-class counts already read back with the previous round, so rows need no extra read-back; the same select over the columns with col_cand, with one read-back of the per-class counts.

5. Hand-over kernels: scatter_col_records_kernel, scatter_row_records_kernel; from milestone 5 write_row_values_kernel (values of a row into csr_val and, by a search over each column, into csc_val).

6. Matrix kernels (milestone 4), from sweeps.cu:649-768 and 1366-1422: keep flag per uploaded slot (not a tombstone, row alive, column not removed) by walk_entries_kernel; scans for positions and row lengths; class key and one stable radix pass over the rows; gather of the kept entries into class order with their order inside a row kept; histogram_kernel (integer atomics, counts only) and a scan for the column lengths, class key and stable pass over the columns; transpose by a stable cub::DeviceRadixSort::SortPairs on (column position, CSR position) and a gather; chunk tables. Compaction of an existing image uses the same steps from the device arrays. Not used: the scatter transpose with an atomic cursor and cuOpt's binning with atomics, whose order depends on timing.

7. Result kernels, from fixed_costs.cu:831-855 (reader): three ordered selects over host indices (col_changed, col_impl, row_next of the last round) and gather_records_kernel into the download buffer. The unordered lists with an atomic cursor are not used. Milestone 1 downloads the mark and value arrays whole instead.

What is taken from cuOpt's load-balanced code (cpp/src/presolve/load_balanced_*; from the reader's report): the structure, that is lines binned by length, sub-warp groups, one block per medium line, a two-level scheme for long columns, an activity sweep and a bound sweep that each write only what the other reads, and the bin key. Its arithmetic is not lifted (plain sums, no counters, side minus activity first, paired results), nor its binning, its second matrix copy, its small-model path or its loop control, and the four defects the reader found are not copied. Variants to time before any replaces the current kernel: class lookup of a warp by ballot against the loop of light_slot; four entries per lane and block sizes 64 and 256 for columns; explicit CUDA graphs for the flag form, whose grid is fixed between builds. For rows, four entries per lane cannot be used: the host order allows two.

Determinism of the whole set: every floating-point sum has one order fixed by the rank of an entry in its row, and the tree depends on the row length only; every reduction across rows is max or min under a total order; integer atomics are used for counts and sums of integers and for a minimum of column indices; marks are stores of one value; contraction is off in both compilers and the only fused multiply-add is the explicit one in two_prod.

===== ROUND_PROTOCOL =====
One call of device_propagation_t::run (G/src/device_protocol.cpp). The same code drives the reference backend and the CUDA backend.

0. Selection, from numbers that are the same on every machine. Not selected when engine is host, in the first cascade of a presolve (result.rounds is 1) unless first_cascade is set, from 2^31 - 1 free nonzeros, or when plan_memory exceeds a set byte_budget. With engine device: selected. With engine automatic: st.free_nnz() >= min_nnz; frontier work F, the sum of 8 + csr.size[row] over the live rows of the propagation list, at least frontier_work plus the entry estimate; and the entry estimate plus one round fits into what is left of fixed_cost_per_nnz times the input nonzeros. Entry estimate = call_fixed_work, plus build_work_per_nnz * live_nnz when the image has to be derived again, or compact_work_per_nnz * live_nnz when only a rebuild was noted, plus sync_work_per_change times the number of changes counted since the last hand-over (differences of bound_changes, side_changes, coefficient_changes, live_rows, live_cols, capped at rows + columns). Nothing is read from the device. The estimate does not depend on a setting of the second group.
1. If budget.stop() already holds, return stopped and leave the list. Otherwise take the propagation list and drop dead rows: frontier F0.
2. Hand-over (interface, C). Afterwards the backend holds the image of the current host state and its sides, bounds and flags.
3. start(F0): row_front is set for the rows of F0; the marks and the implied candidates of the call are cleared. Rows, entries and per-class counts of F0 are computed on the host from csr.size, so the first round needs no read-back.
4. One round on the frontier F, inside the backend:
 a. Fold both activities of every row of F from scratch, from the bounds as the device holds them (entries of fixed columns with their value): hi, lo, count of infinite terms, largest finite term.
 b. Candidates: for every live column with an entry in a row of F, and for each such entry, the tests and the arithmetic of rules_propagation.cpp:51-73 and 111-126 on those activities: side finite and |side| * side_error <= feasibility; two or more infinite terms give nothing; exactly one gives a candidate only to the entry whose own term is the infinite one; without one the own term is removed first and the update count is the number of finite terms plus one; no candidate when activity_error(updates, max_term) > activity_error_share * feasibility * |a|; bound = dd_residual(side, rest) / a, dropped when not finite. Rows outside F give nothing: none of their columns changed since they were last examined. Integer column: the candidate is moved outward by 4 rounding units of its size. Per column the largest lower and the smallest upper candidate are kept, each with its row, equal values going to the smaller row index.
 c. Apply, all columns together on the bounds of the snapshot. Integer column: the two best candidates are rounded with the feasibility tolerance (ceil(l - feas), floor(u + feas)); L = max(lower, rounded lower), U = min(upper, rounded upper); L > U is infeasible; otherwise the column takes L and U and is fixed when they are equal. Rounding after the reduction gives the same value as rounding each candidate, because the rounding is monotone. Continuous column: the explicit bounds are never written; the best candidate of the call per side is kept with its row.
 d. Next frontier: the alive rows of the columns whose bound changed in this round. An implied candidate alone puts no row into it, as on the host.
 e. round_status_t is read back: one read-back per round in the flag form, two in the list form (the second sizes the column lists).
5. After a round, on the host, in this order. infeasible_col >= 0: the call ends with outcome infeasible and nothing is handed back. Otherwise the budget is charged 8 * front_rows + front_nnz + 8 * cand_cols + cand_nnz + changed_nnz, and budget.found() is called when changed_cols > 0. These numbers are defined by the frontier and by counts of entries in alive rows, not by the form of the sweep or by dead rows still in the image, so every form and both backends charge the same. Next frontier empty: the call is complete. budget.stop(): stopped. The fixed-cost budget cannot cover another round: hand back. The work of the next frontier (8 * next_rows + next_nnz) below handback_work in handback_rounds consecutive rounds: hand back. Otherwise the next round runs on the next frontier. The form of the next round (lists when the image has at least list_min_nnz nonzeros and the frontier work is at most list_share of the matrix work, else flags) changes no result.
6. finish(): changed integer columns in ascending index with their bounds, continuous columns with a candidate in ascending index, pending rows in ascending index. With phase_hashes a hash over these lists and every round_status_t is appended to result_t::device_hash.
7. Replay on the host, ascending column index. Integer column: if L > col_lower, tighten_lower(st, ps, col, L); then, if the column is still live and U < col_upper, tighten_upper(st, ps, col, U). Each change is one finding. L <= U <= old upper holds, so neither call can report infeasible (asserted), and a column with L == U ends fixed with its postsolve record, in ascending column order. Continuous column, lower then upper: the host's own test (the valid record or the infinity, improvement by more than implied_bound_step * feasibility) and record_implied_lower / record_implied_upper with the row; each record is one finding. Activities (two terms per changed bound, never a * (new - old)), lists, counters, row_free_size, the objective offset and the records follow from the host operations.
8. List repair. The replay has pushed the rows of all changed columns on the propagation list. The list is taken and only the pending rows are pushed back, in ascending index. A row of a changed column that is not pending was examined in a round after the last change of any of its columns, so the host rule would find nothing new on it. The row_rules and tightening lists keep what the replay pushed.
9. Return findings, stopped and outcome. If the call was not stopped and rows are pending, the driver runs the host rule on them with the same budget.

Why a device result is valid in floating point.
- The fold of a row on the device has the bits of state_t::fold_row_activity for the same entries and bounds: same lanes, same operations, same tree. Assertion builds compare every alive row after every hand-over, tests compare all length classes.
- A device candidate is therefore the value candidate() returns on a host state in which that row was just recomputed, a state the host produces itself (construction, a stale row, scale_row, compaction). The guard is the host's expression with the smallest update count a row can have; the device adds no numerical assumption of its own. The known weakness of the guard formula (state.hpp:415-419: it is not a proven bound) is inherited unchanged.
- The bounds a round reads are valid for every feasible point (by induction over the rounds) and the row is the host's current row (hand-over). Each candidate is then true for every feasible point; the maximum of true lower bounds and the minimum of true upper bounds are true; applying them together is the rule of validity class B (DESIGN.md section 4). A column tightened in the same round was used by other rows with its wider bounds, which is weaker, not wrong.
- Outward move and integer rounding are the host's functions. L == U of two valid integral bounds is a valid fixing, L > U a valid infeasibility.
- Continuous columns get records only. The record's row cannot change or die during the call, and a bound derived from wider bounds of the other columns stays implied by that row under the tighter ones.
- The host accepts the result only through tighten_lower and tighten_upper, which never relax a bound.

Why the result is the same on every run, thread count and GPU type.
- Sums have one order fixed by entry position; reductions across rows are max and min under a total order; counters are integer sums; marks are stores of one value.
- Only IEEE addition, subtraction, multiplication, division, the explicit fma, comparisons, ceil and floor are used; contraction is off in both builds.
- What reaches the host is in ascending column index, and the replay is sequential host code.
- Only the settings of the first group decide which engine works on what, and they are functions of the model and the settings. The settings of the second group, the backend and the memory path change no result (tested by equal hash sequences).
- Host and device are not required to agree with each other: the device applies a round from one snapshot, the host row by row. Equality between them is claimed only on integer models with exact data run to an empty frontier.

Deviation from the plan, on purpose: DESIGN.md 2.2 says the dirty lists carry bounds, accumulators and counters as bits. Here only bounds and implied candidates cross, and the host accumulators stay the host's own two-term sums. Writing device sums into the host would need exact int32 counts, slot sums and a new state operation that repeats fix_col's bookkeeping. The replay costs the entries of the changed columns on the host, which is what the host engine pays for the same changes. The bit hand-back is a measured variant (decision for the owner).

===== MEASUREMENTS =====
Conventions. Warm: the context, slabs and pinned staging exist before the timed call; the tool creates them and runs one untimed presolve first; the cold start is reported apart. The timed interval is the existing one, from the input CSR to the finished reduced model, so builds, transfers and the replay are inside. Each figure is the minimum of at least three alternating runs; device runs take the same lock as the single-core host timings. Results go to G/results/stage1/device/<tag> with source checksum, binary checksum, host and load. Dev-node runs stay small; the second GPU type and the long device campaign are cluster jobs on a wide set.

Tools. gprs_device_bench (G/device/bench) times kernels and steps on an image with a frontier; its inputs are states that gprs_presolve writes at every propagation call of the 40 instances (model, bounds, list), so frontiers are real ones. gprs_presolve_device --device-log writes one line per propagation call and round (frontier work, rows, entries, changes, seconds for hand-over, build, fold, candidates, read-backs, result, replay, host rule after it). With --shadow the tool copies state and postsolve stack before a propagation call, runs the host rule on the copy with a timer and discards it; that gives host time and device time for the same state and frontier.

The third list of DESIGN.md:678-689, item by item, and what each result settles.
1. Frontier kernel in lane-group order, frontier-restricted candidate step, whole GPU step: flag form against list form against the serial lane kernel at frontier shares from 0.01% to 100% of the rows and on recorded frontiers; candidate kernels over all columns against column lists, with the scan of long columns that have one frontier entry reported apart; the whole round by part. Settles row_form, col_form, list_min_nnz, list_share (the plan's share above which all rows are recomputed). Decision 5: the lane order is kept in every case, because the serial kernel has the same bits; 'slow' is read as a scheduling question, and the lane-group list form is kept wherever it is not slower than the serial lane kernel.
2. Host engine with incremental activities on the same calls, frontiers between 10% and 100% of the rows, consecutive small rounds per cascade, and the replay time per changed column entry: from the shadow log. Settles frontier_work, handback_work, handback_rounds, min_nnz.
3. Fold, candidate sweep, image build and compaction on the models of 20,000 to 70,000 nonzeros that occur as instances shrink (ns1830653 and others). Settles the lower end of min_nnz, image_on_device_nnz, the build and compaction constants.
4. The ordered result lists and the hand-over on model-sized states: records at 0.01% to 25% of rows and columns against whole arrays. Settles sync_list_share and sync_work_per_change.
5. Layout and bins: state arrays in class order against host order; entries in class order as built against the Stage 0 second copy; re-binning inside the build; row_light_max 32 against 64; other column boundaries and cuOpt's column parameters; the cost of the guard loads; lo always against on a flag; CSC values against an index into the CSR values.
6. Large end: rows above 1e7 nonzeros, lane groups against the serial lane kernel; columns from 1e6 nonzeros, lane groups against one thread per column; the latency of rows above 8,192 entries with one block per row, on square47 and the other instances that have them and on a synthetic row of 1e6 entries, against a bench-only chunk kernel (done in milestone 3, because it feeds a decision).
7. A second GPU type: hash sequences and the times of items 1 and 3.
Variants, each timed before it replaces the current kernel: hand-written block tree against the Stage 0 cub::BlockReduce time; count through the shuffles against the integer atomic inside lane groups; ballot against loop for the class lookup; a CUDA graph per round against separate launches; round stamps and lists claimed inside the kernels (integer exchange, slots reserved per block) against cleared marks and ordered selects; a gate word per row against loading count, lo and max_term; a row-driven candidate step that emits candidates of the frontier entries and reduces them after a sort by column; bit hand-back of accumulators against the replay; event records against whole arrays.
Also due in Stage 1b: the dead-entry fraction of a rebuild (the host fractions swept on the host engine; for the image the share of entries in dead rows that triggers a compaction, which changes no result) and the device fixed-cost budget.

How a threshold is fixed. Settings of the second group are set to the fastest choice per size class and can be changed later without a new hash. Settings of the first group are fixed once, in the order frontier_work, handback_work and handback_rounds, the estimate constants, min_nnz: each at the value with the smallest summed time of the logged propagation calls over the testbed, the device being taken only where it beats the host by more than the run noise (ties to the host), and under the condition that with the defaults no instance is slower than host only by more than the larger of 5% and 2 ms on the minimum of three alternating runs. After each value the oracle campaign runs with the new defaults.

Final runs and gates. Host only, device with defaults and device forced, three alternating runs each on the 40 instances: per-instance time rule, band geomean and median, reductions ratio against the reference and against host only, row dynamism. Host-only results must be unchanged. The reductions gate is one-sided: an instance on which we leave fewer nonzeros than the HiGHS reference passes, as the owner said in the message that started this run; only a geometric mean below 0.99 or an instance below 0.95 needs an explanation. The ratio of device-forced runs against host-only runs is reported as well, because rounds from one snapshot can use the budget differently.

Expectation, inferred from stored results the reader quotes (propagation is 5.5 of 82.7 s): the device cannot gain more than a few percent of the presolve time at Stage 1, and min_nnz may come out above every testbed size.

===== RISKS =====
- Performance. Bound propagation is about 7% of the host engine's time in the stored results (reader's figure), the first and largest call stays on the host by the plan, and deriving the image costs a pass over the nonzeros. With honest thresholds the device may be selected on few testbed instances or on none; all tests therefore force it, and the default stays host until milestone 7.
- Rounds from one snapshot need one round per link of an implication chain, and the work charged per round includes the entries of the candidate columns. A wide slow chain can use up the budget of 16 passes earlier than the host rule would, and then fewer bounds are found. The reductions ratio of device-forced runs against host-only runs is reported for this reason; the hand-back rule limits the effect but its two values can change results and must be right when they are fixed.
- Candidates are reduced per column, so a small frontier that touches a very long column makes the device scan that whole column while the host reads one entry. The selection before the first round does not see it. Milestone 6 measures it; the remedy that needs no rule change is the row-driven variant with a sort by column.
- Rows above 8,192 entries are folded by one block with row length / 256 entries per thread (about 0.5 to 0.6 microseconds per entry per thread on the H200, from README_sweeps.md through the reader). A row of a million entries costs about 2 ms per fold. The chunk rule removes this but changes activity_lanes for both engines and the stored host hashes of the instances with such rows.
- Before milestone 5 any coefficient change (row tightening changes values in most cascade passes) makes the whole image stale, so the device is rarely selected after the first pass of a cascade. After milestone 5 only doubleton substitutions and host rebuilds force a new image, at most once per presolve round and phase.
- The journal of milestone 5 is the one place where a missed event gives an invalid result, not only a slow one: a row whose coefficient and side were changed by tightening is a different constraint, and a stale device copy can cut off feasible points. Guards: the journal test on the Mac, the campaign with the reference backend, the comparison of image and mirrors with the host after every hand-over in assertion builds, and in release builds a check that the journal's event counts agree with the hashed counters.
- The reference backend and the CUDA backend share propagation_rule.hpp, so a wrong rule is wrong in both and their equality does not show it. The independent checks are the refactor test (host hashes unchanged proves the header is the old host rule), the oracle, the campaign, the mutants and the check tool on real instances.
- The guard updates * u^2 * max_term is known not to be a proven error bound (state.hpp:415-419). The device uses it with the smallest update count a row can have and inherits the host rule's exposure exactly; it does not repair it. A change of the guard is made once in propagation_rule.hpp for both engines.
- Sharing numerics.hpp with device code rests on nvcc accepting std::fma and the other std math calls in host-and-device functions (inferred, not checked). Milestone 1 settles it; the fallback is a device copy tied to the host by test 12 alone.
- Bit equality across GPU types rests on IEEE behaviour of the basic operations, fma, ceil and floor with contraction off, and on order-preserving selects and stable radix sorts in CCCL (from memory). It is proved only by a run on a second GPU type; a compiler or CCCL upgrade needs tests 15 to 19 rerun.
- The edits of numerics.hpp, rules_propagation.cpp, presolve.hpp, presolve.cpp and, in milestone 5, the state files change the run identity. Stored host timings must be run again once after milestone 1 and once after milestone 5, and each time every host hash must be shown unchanged.
- Device memory: about 52 bytes per nonzero at the peak of a build on the device (estimated from the array list). The byte budget is due only before Stage 2; until then the largest instances may not fit next to other users of the GPU, and a failed allocation is a hard error.
- The managed path is functional only. Forced on x86 it faults at every hand-over, so its tests stay on small models and say nothing about Grace Hopper; it also keeps two copies of the matrix there.
- Fixed costs. A round has one read-back in the flag form and two in the list form, and the list form's selects, statistics and cleared marks are passes over all rows and columns; with many small rounds these dominate. The stamp-and-claim variant removes the passes but is not the first version, because its list order depends on timing.
- The temporary storage of CCCL calls is taken from the scratch slab with sizes planned from the input model. If a CCCL version asks for more, the engine stops with an assertion; the plan needs a margin and a test on the largest instance.
- A device campaign costs about a millisecond per model (estimate), so the dev node runs two million per build and the tens of millions run on the reference backend. A kernel error that shows only on rare inputs is covered by the per-call comparison with the reference in the assertion build, not by volume. The node can drop: builds, recorded states, logs and campaign parts are kept on the scratch with step markers so that a run restarts where it stopped.

===== DECISIONS FOR OWNER =====
- Hand-back. DESIGN.md 2.2 says the dirty lists carry bounds, accumulators and counters as bits. This design hands back bound changes and implied-bound candidates only and lets the host apply them through tighten_lower / tighten_upper; device sums never reach the host accumulators. Is this deviation accepted for Stage 1b, with the bit hand-back kept as a variant that milestone 6 measures (it changes hashes and needs a new state operation, so it would have to be adopted before the thresholds are fixed)?
- Rows above 8,192 entries. The plan says chunks in 2.3 and one block in 2.4; the host code sums every row above 64 entries with 256 lanes over the whole row. The design keeps the host order and changes no host bit. A chunk rule for both engines removes the latency of very long rows but replaces the stored Stage 1a hashes of the instances that have such rows (5 of the 32 Stage 0 matrices). Milestone 3 delivers the numbers; the choice is yours, and it should be taken before milestone 6.
- state_t inside the presolve memory resource. A single copy of the matrix read in place by both engines on Grace Hopper, and a device rebuild that replaces state_t::rebuild instead of rebuilding only the device's copy, both need state_t's arrays allocated from the resource, which changes the array types in state.hpp for every rule. In Stage 1b the design keeps std::vector storage and a second copy on the device. Do this in Stage 1b, or with the overlay design before Stage 2?
- Is an integer atomic minimum or maximum on an order-preserving 64-bit image of a double within 'no floating-point atomics'? Its result does not depend on order. It would allow candidates to be reduced per frontier row inside the fold, without scanning long columns. The design does not use it; the question is whether it may be built as a benchmarked variant.
- Machines. Which GPU type on the cluster serves as the second type for the hash comparison, and is a GH200 node available (open item 1 of the plan)? Without them both checks stay at 'same GPU type' and 'managed path forced on x86'.
- If milestone 6 shows no model size at which device propagation beats the host by more than the run noise: ship device propagation off by default (the infrastructure kept for Stage 2), or keep the plan's default of 5e5 nonzeros at a known cost?
