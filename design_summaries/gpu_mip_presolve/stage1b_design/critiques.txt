
===== CRITIC validity =====
VERDICT: I could not break the device round itself. Two serious defects sit at its edges (the hand-over check from milestone 5 on, and the byte budget), plus two minor ones.

**What I read:** numerics.hpp, state.hpp, rules.hpp, presolve.hpp, rules_propagation.cpp, rules_bounds.cpp, state_ops.cpp, state_build.cpp, presolve.cpp, hash.cpp, state_storage.cpp 1-240, sweeps.cu 180-660, tests/oracle.hpp, tools/gprs_fuzz.cpp, test_propagation_bounds.cpp 296-495, DESIGN.md 1-450 and the synthesis notes. Nothing was built or run.

**What holds against the code:**
- **Fold bits:** a device fold that skips infinite terms has the bits of the host fold, because a lane never holds -0 and the host adds a * 0 (state_build.cpp:67-97, 115-125, 176-209).
- **Guard:** the device's update count (finite terms, plus one when the own term is removed) is what the host stores after a fold (state_build.cpp:223, rules_propagation.cpp:60-69). The host guard is never weaker.
- **Rounding:** rounding after the max/min reduction equals rounding each candidate, since the outward move and ceil/floor are monotone.
- **Replay:** tighten_lower / tighten_upper cannot report infeasible for an integral L <= U and fix the column when L == U (rules_bounds.cpp:15-49).
- **List repair:** a row that is not pending was examined after the last change of any of its columns.
- **Hand-over counters:** every device-relevant change moves bound_changes, side_changes, coefficient_changes, live_rows or live_cols; only rebuild does not (state_ops.cpp:195, 288-299, 353, 373, 386, 398-403, 426-433, 455, 478, 519; state_storage.cpp:116-219).
- **Storage order:** rebuild and compact_sparse_lines keep the order of live entries in a row.
- **Cascade edits:** no entry is added, deleted or moved inside a cascade (grep over src/rules_*.cpp).

**Not checked:** the reader reports are not on disk (their directories are empty), so everything the design takes "from the reader" (cuOpt's load-balanced files, fixed_costs.cu, stored timings) is unverified by me. Statements about CCCL internals are from memory.

[serious] The hand-over check is defined against make_device_image(st), which excludes dead rows, while the design keeps dead rows in the device image until a compaction. The two cannot be equal array for array after the first row deletion.
  WHY: The design says both 'A dead row is not in the image' (definition of make_device_image) and 'Such rows stay in the image as dead rows (row_alive 0) until a compaction'. delete_row moves only live_rows and live_nnz (state_ops.cpp:331-362), so by the hand-over rule only the row mirror is sent and the image is kept. Row rules delete rows in almost every cascade pass (rules_rows.cpp:65, 117, 164, 203). After that, row_start, row_id, row_pos, col_start, csc_row, csc_val and the class plans of the device image all differ from make_device_image(st), so the comparison 'after every hand-over' fails or has to be weakened. The only other check named is the fold of every alive row, which reads csr_val and the bounds only. The candidate kernel takes its coefficient and row from the CSC (sweeps.cu:579-580, 606-607). From milestone 5 on csc_val is written in place by a search (write_row_values_kernel), and the design itself calls this the one place where an error gives an invalid bound. A wrong csc_val then passes every assertion; it is seen only where the CUDA and reference backends happen to differ, or where the oracle optimum moves.
  FIX: Define one comparison of a device image against a host state that may have lost rows since the last build or compaction. For every alive host row, the image row equals the host's live (column, value) list in storage order and row_len equals csr.size. For every column, the image's CSC entries whose row is alive equal the host's (row, value) set of that column in ascending row_pos. The layout arrays equal those stored at the last build. Run it in assertion builds after every hand-over on both backends, and add a wrong-kernel build that writes a wrong csc_val and must fail it.

[serious] Eligibility under a set byte_budget is computed from plan_memory(nrows, ncols, nnz, options), whose result depends on settings the design lists as unable to change a result, and on the machine.
  WHY: Step 0 says the device is not selected 'when plan_memory exceeds a set byte_budget', and byte_budget is in the group that can change a result. plan_memory returns the matrix, state, scratch and staging slabs. The staging slab (64 MiB) exists only on the pinned path. The managed path is chosen by a device attribute on Grace Hopper. Build scratch of about 28 bytes per nonzero exists only when the image is built on the device (image_build, image_on_device_nnz). So near the budget the same model and first-group settings run the device rounds on one machine and host-only on another, and the reduced model differs. This breaks 'Nothing is read from the device' (DESIGN.md 2.1, lines 160-161) and the guarantee of 2.5. It is dormant while byte_budget is 0. No listed test sets a byte budget while varying memory_path or image_build, so tests 8 and 19 would not see it.
  FIX: Compare byte_budget with one canonical figure that is a function of rows, columns, nonzeros and first-group settings only, for example the maximum over both memory paths and all build choices. Keep plan_memory's path-specific sizes for allocation only. Add a test that repeats tests 8 and 19 with byte_budget just above and just below the canonical figure.

[minor] The size limit for eligibility is stated on free nonzeros, but the image holds live nonzeros (entries of fixed columns included), and the device build indexes the uploaded host slots with 32-bit positions.
  WHY: The design excludes the device 'from 2^31 - 1 free nonzeros' and says 'Entry positions inside build and compaction are 32 bit'. free_nnz() is live_nnz - fixed_nnz (state.hpp:272). The image row is 'the live entries of host row i, entries of fixed columns included', so it has live_nnz entries. fixed_nnz is not bounded inside a cascade: the state is rebuilt only between phases (presolve.cpp:232-244), and forcing rows and dual fixing fix columns within a cascade. The device build of milestone 4 uploads the host CSR slots, tombstones included, so its positions run over csr.slots(), which is larger again. A model with free_nnz below 2^31 and live_nnz or slots above it overflows the 32-bit positions. In a release build that is a wrong image with no check. It needs a model above about 2e9 nonzeros, so it is an edge case.
  FIX: Test eligibility on the quantity each path actually indexes: live_nnz for a host-built upload, csr.slots() for a build on the device. Assert the same bound inside build and compaction in every build type.

[minor] The device-round rule cases (test 4) leave out the two host cases that separate the outward move and the error guard from a wrong rule, and campaign models cannot stand in for them.
  WHY: The mutant lists require 'no outward move' (test 10) and 'guard dropped' (test 20) to fail. The host cases that pin them are propagation_large_bound (test_propagation_bounds.cpp:357-384, where the candidate is off by 1e-5 at 5.7e10) and propagation_error_guard (300-317). Test 4 names lines 140-161 and 341-357, the 513-term row and a list of other cases, but neither of these. A mutant inside propagation_rule.hpp is still caught by the existing host tests, because the host rule calls the header. The device's own call sites are not: the outward move before the reduction in device_reference.cpp and the kernels, and the guard inside the candidate kernel. Oracle and campaign models have integer data on which 'every sum is exact' (oracle.hpp:21-22, 72-73). A guard rejection needs a term near 1e20 together with a coefficient scaled down to about 1e-6, so those two mutants would be caught by chance only.
  FIX: Add both cases to test 4, run through a device round on both backends with integer columns. Add recorded inputs for tests 15 to 17 on which the guard rejects a candidate.

The replay rounds L again inside tighten_lower (rules_bounds.cpp:19); that returns L only for an integral L and a feasibility tolerance below 1. The tolerance is an input (options_t::tol), so the precondition should be asserted in reset().
- A direct test of decide_integer_bounds and better_lower / better_upper against tighten_lower / tighten_upper on a one-column state with random values. The host rule does not call these functions, so the acceptance test 'every host hash unchanged' proves the header equal to the old host rule only for the candidate functions; the risk text claims more.
- A statement of what is compared for a round that ends infeasible. Test 16 compares every round_status_t, and the kernels still apply and count the other columns in that round, so the reference backend must finish the round instead of stopping at the first infeasible column, or the other fields must be excluded for that round.
- A test with byte_budget set (see the second defect). Every listed determinism test runs with the default of 0.
- A check per GPU type that the scratch slab covers what the CCCL calls request. From memory, the temporary storage of cub::DeviceSelect depends on a tile size taken from an architecture-specific tuning policy, and the project compiles with CMAKE_CUDA_ARCHITECTURES native. The request is then not a function of the input size alone, and the hard assertion could fire on one GPU type and not on another. I did not verify this in the CCCL source.
- The second GPU type and a Grace Hopper node. Bit equality across GPU types and the managed path remain unproven until they are run, as the design says itself.

===== CRITIC performance =====
VERDICT: The design is careful about bits and about what can change a result, but as a performance design it is aimed at the wrong place, and its milestones find that out last. I checked this against the stored Stage 1a results and with a logging probe that I built in my scratch directory from a copy of the host sources and ran on the 17 CSR dumps in gpu_presolve/local_dumps (nothing in the worktree was touched; counts are machine independent, seconds are Mac seconds and used only as ratios). Measured: in the stored node results (40 instances, results/stage1/host/v3) bound propagation is 6.9% of the host time (5.14 of 75.0 s) and state construction is 45.7%; propagation work is at most 1.10 passes on 35 of 40 instances and 10 instances call propagation once. In the probe the first propagation call of each instance holds 92.5% of all propagation work, the calls of rounds 2 and later hold 6.1%, and of the 392 calls none passes the design's default selection (not in the first cascade, 5e5 free nonzeros at the call, frontier work 20,000): the seven calls with enough frontier work are on models that have shrunk below 5e5 nonzeros by then, and they change 0 to 10 bounds each. So milestones 2 to 5 build, and milestones 6 and 7 tune four result-changing thresholds for, an engine whose operating region is empty or a handful of calls on the testbed. Beyond that, several parts cost work proportional to whole columns, to rows plus columns or to all nonzeros when the frontier is small, the shipped threshold shape (constants in units of 10 ns) cannot fit both 5e5 and 2.6e8 nonzeros, and some of the claimed measurements cannot be made with the described harness. Two things I checked and found not to be a problem at the measured scale: the rounds-from-one-snapshot scheme needed only 1 to 3 rounds on the calls after the first cascade (up to 14 on a first call), and running the host rule on a copy of the state biased its time by a factor 0.97 to 1.88 (mostly 1.05 to 1.35), not by the factor 4 to 7 between warm and cold that Stage 0 reports. My notes are in /private/tmp/claude-502/-Users-acoerduek--claude-spares-spare-bsnTJo/c660eb6b-7edc-4afc-bf62-0442cb32d870/scratchpad/stage1b_design/critic_performance/notes.md, the probe and its output per instance in the probe/ directory next to it (probe/src/probe.cpp, probe/out/*.txt, probe/summarize.py).

[blocks] The selection rule gives the device only the propagation calls where there is almost no work, and the milestone order measures this last. The device is excluded from the first cascade, needs 5e5 free nonzeros at the call and frontier work of 20,000; the logs that would show how many calls qualify (device log, shadow run, recorded states) are in milestone 6, after the block and chunk kernels, the list forms, the device rebuild, the journal and the managed path are built.
  WHY: Read from the stored node results (results/stage1/host/v3, 40 instances): propagation is 6.9% of the host time, its total work is at most 1.10 passes on 35 of 40 instances, and 10 instances call it exactly once. Measured with my probe on the 17 local dumps: the first call holds 92.5% of all propagation work; calls in rounds 2 and later are 257 of 392 calls (236 of them unitcal_7 with a median frontier of 963 units) and 6.1% of the work; only 7 have frontier work of 20,000 or more (ravan 73,404; radiationm18 94,842 and 49,130; rd-rplusc-21 727,736; uccase9 191,120 and 52,789; unitcal_7 28,384) and none of them is on a model with 5e5 free nonzeros at that call (ravan has 468,648 left, rd-rplusc-21 352,318). Those 7 calls change 0, 10, 0, 5, 0, 0 and 2 bounds. For the instances I do not have locally: of the 24 that start at or above 5e5 nonzeros, 7 call propagation once and 5 end below 5e5, which leaves 11 instances with at most 25 calls after the first one. The thresholds of milestone 7 would be fixed on that sample. The question needs no device code: it is a per-call log of the host engine.
  FIX: Make a per-call propagation log the first milestone, host only, on the node for all 40 instances: presolve round, cascade pass, live rows on the list, frontier work, the host's own work, bound changes, seconds, and the round counts of the reference backend's replay. Then decide with the owner before any further device kernel is built: either the device may take the first propagation call of a presolve, which is a full-list sweep and the only case where the Stage 0 numbers say the GPU wins clearly (kenana: 45.6 ms on the host for that call against roughly 10 ms for upload, build, one sweep and hand-back, inferred from Stage 0 figures, not measured), which contradicts the plan's rule that the first cascade runs on the host and needs an image of the input model; or Stage 1b is infrastructure only, and then the device rebuild, the journal and the managed path wait until a Stage 2 consumer fixes what they must do, and the engine default stays host without a threshold campaign.

[serious] The candidate step reduces per column over the binned CSC, so every column that has one entry in a frontier row is scanned in full, in the flag form and in the list form, and the work charged to the budget contains those whole columns (8 * cand_cols + cand_nnz).
  WHY: Measured with the probe on the calls after the first one (first round of each call): the entries of the candidate columns are 1.3 times the frontier entries on radiationm18, 2.2 on uccase9, 3.6 on unitcal_7, 5.5 to 14 on istanbul-no-cutoff, 6.1 on brazil3, 8 to 29 on ravan (one call has 24 frontier entries and 11,828 column entries) and 73 and 278 on rd-rplusc-21 (706 frontier entries, 196,527 column entries). The design's charge against the host's work on the same call: ravan round 2 309,898 against 76,681; rd-rplusc-21 201,297 against 2,714 and 775,820 against 34,284. Stage 0 has no number for this: README_sweeps.md lists 'no frontier-restricted candidate kernel on the device' under limits and the report says the whole step is modelled. The design names the problem as a risk and leaves the remedy as a variant for milestone 6, but the remedy changes the kernel family, the list forms and the charge, and the charge is in the group of things that change a result: a row-driven step would have to count whole columns only to keep the hashes. Inferred from DESIGN.md section 7: a probe must cost work proportional to the entries it touches, with bound merges per column by min and max, so the column scan is also the one Stage 1b kernel that Stage 2 cannot reuse.
  FIX: Make the row-driven step the baseline for frontier rounds: the threads that fold a frontier row emit a candidate per entry (the row's activities are already in the group), and the candidates are reduced per column by a sort and segmented min/max, or by an integer atomic min/max on an order-preserving 64-bit image if the owner allows it (the design already asks this question). Keep the CSC scan for full sweeps, where it is the kernel Stage 0 measured. Define the charge of a round without whole columns (frontier rows and entries plus the entries of changed columns, as the host charges), so that both candidate forms give the same hashes.

[serious] The result-changing thresholds are constants (frontier_work 20,000, handback_work 20,000, call_fixed_work, round_fixed_work) in work units of 10 ns, while the cost of a device round grows with the image (flag form: a full sweep) or with rows plus columns (list form), and the host does not cost 10 ns per unit.
  WHY: From the stored node results the host engine's propagation costs a median of 5.5 ns per work unit (0.9 to 12.0 over the 40 instances); the 10 ns of Stage 0 came from a benchmark that recomputes activities, which the engine does not do. So 20,000 units are about 0.11 ms of host time. A flag-form round is one full sweep: the best compensated sweep of Stage 0 is 282 microseconds in band B1, 390 in B2, 741 in B3 and 3.1 to 24.7 ms on the nine matrices above 1e7 nonzeros, plus the fixed-cost step of 77 to 93 microseconds. In host terms that is about 65,000 units at 5e5 nonzeros and 150,000 in B3, so with handback_work at 20,000 every round between 20,000 and that figure is a loss, by a factor 3 to 7 in band B and far more above 1e7. A one-round device call below 1e6 nonzeros adds about 0.3 ms of launches, clears, read-backs, record uploads and the three ordered selects of the result (Stage 0: launch 9.0, read-back 13.8, select 23 to 46 microseconds each) to the sweep. The rule of milestone 7, one value per setting with the smallest summed time, cannot repair this: any single constant is wrong at 5e5 or at 2.6e8 nonzeros.
  FIX: Express the selection and the hand-back as a comparison of two estimates that are functions of the model and the settings only: the host's work for the frontier, and the device's work for the round in the form it would use, a + b * image nonzeros for the flag form and a + c * (rows + columns) + d * frontier work for the list form, plus a call term with the same structure. Fix the coefficients by measurement instead of the four constants, and measure the host's cost per unit on the engine itself before any threshold is quoted in units.

[serious] The selection measure F (8 + csr.size per listed row) and the device fold ignore what the host does in constant time: a side with two or more infinite terms costs the host nothing, a side with exactly one costs one entry (rules_propagation.cpp:119-127), and the terms of fixed columns are already inside the maintained activity. The device folds every listed row in full, entries of fixed columns included, both sides.
  WHY: Measured with the probe: on var-smallemery-m6j6 the passes after the first list 151 rows with one infinite term; F is 819,847 and the host's work is 1,508 to 4,086 units, a factor 200 to 540; those rows hold 818,639 live entries while the whole model has 575,217 free nonzeros, so at least 243,000 of the entries the device would sum are constants of fixed columns. supportcase42 (94% of the rows with two or more infinite terms, per the Stage 0 report): F 583,165 against 147,512. rd-rplusc-21 round 2: 727,736 against 442,393. The extreme cases I saw are inside the first cascade, which the default excludes, but the structure stays for the whole presolve: Stage 1 never tightens the explicit bounds of continuous columns, and Stage 0 counts rows with exactly one infinite term as at least 10% of the rows on 6 of 31 instances. With F as it is, the device is selected for calls the host finishes in microseconds, and its budget charge runs ahead of the host's by the same factor.
  FIX: Compute the frontier work from the host's exact counters, at no extra cost per row: per usable side, csr.size when the count of infinite terms is 0, 1 when it is 1, 0 when it is larger. Drop rows without a side that can give a candidate from the first frontier before the upload; they come back through the next-frontier marks if a column of theirs changes. Charge the device round on the same basis. That the device sums the constants of fixed columns again in every round follows from the bit-equality rule and should be stated with its price, measured on recorded states.

[serious] The list form, which is the form for small frontiers, still makes passes over all rows and all columns in every round (an ordered select over the row positions, one over the columns, the frontier statistics kernel, cleared mark arrays) and in every call (cleared marks and four implied-candidate arrays, three ordered selects for the result). The variant that removes them (round stamps and lists claimed inside the kernels) is left for milestone 6 with the reason that its list order depends on timing.
  WHY: Stage 0 fixed costs: an ordered select over a 1e7-element flag array costs 106 to 141 microseconds whatever it selects, copy_if 57 microseconds at 1e6 and 231 at 1e7 elements, a read-back 13.8. A list-form round therefore carries roughly 0.2 to 0.5 ms of selects, statistics and read-backs at 1e6 to 1e7 rows plus columns, which is 40,000 to 90,000 host work units at 5.5 ns. The list form is used only when the frontier is at most 1% of the matrix work, so on every image below about 4.5 million work units the fixed part of a list-form round alone exceeds what the host needs for the whole frontier. On the short-row instances a pass over rows plus columns is not small against the nonzeros: sesia 40.6 million against 47.5 million, dlr2 46.0 against 78.1, kenana 1.2 against 3.0, kasavu 1.67 against 4.24, ravan 0.42 against 0.64. The stated reason for postponing the cure does not hold for these lists: the order of an internal work list cannot change a result, because every fold writes by row index, every candidate reduction writes its own column, and the counters are integer sums. Only the lists handed to the host need a fixed order.
  FIX: Make stamps and per-class lists claimed inside the kernels (integer exchange on the mark, integer atomic cursor per class) the first list form for frontier rows and candidate columns, and keep ordered selects only for the three result lists at the end of a call, or sort those few records on the host. Add a test that permuting a frontier list inside a class leaves every round status and result unchanged.

[serious] Deriving the device image is treated as a device step priced by the Stage 0 figure of 467 microseconds + 0.279 ns per nonzero, and milestone 4 builds a rebuild on the device. But the host state stays the only authority in pageable std::vector storage, so every derivation starts with an upload of the host CSR, and the device rebuild only rebuilds the device's copy while the host still does its own rebuild.
  WHY: Stage 0 measured pinned copies at 50 to 53 GB/s and pageable copies at 9.6 to 11.1 GB/s. The host CSR is 12 bytes per slot, and it reaches the device either through a host copy into the pinned window or as a pageable copy, so the upload costs about 1.1 ns per slot, four times the device build. At 5e5 nonzeros that is about 1.2 ms per derivation, or about 220,000 host work units at 5.5 ns: the frontier has to be a quarter to a half of a full pass before a call that needs a new image can break even. A new image is needed at the first eligible call of almost every round: in the probe, every round 2 has no image yet, and in 11 of the 16 rounds from 2 on the previous doubleton call had moved or deleted entries. The journal of milestone 5 only keeps the image valid inside one cascade, where the later passes had frontier work of at most 53,000 units. The plan's threshold 'rebuild on the GPU from 100,000 nonzeros' is about which engine rebuilds the state; milestone 4 measures a host-built upload against a device build of the same copy, which is a different question, and it cannot shorten the host's own rebuild or the state construction, which is 45.7% of the host time in the stored results.
  FIX: Put the upload into the entry estimate and into the milestone 4 comparison (report build with and without it). Do not build the device rebuild before the owner has decided whether state_t's arrays live in the presolve memory resource (pinned or managed): without that decision the device rebuild has no consumer on the host and the upload stays at pageable speed. If the decision is no for Stage 1b, keep the image as a host-built upload and move the device build and compaction to the stage that needs them.

[serious] Rows above 8,192 entries are folded by one 256-thread block per row, row length / 256 entries per thread, to keep the order of numerics.hpp. The design quotes 2 ms for a row of a million entries and offers the owner one alternative, a chunk rule that changes the host bits.
  WHY: Read from the stored Stage 0 matrix data (results/stage0/sweeps and sweeps_large): such rows exist on 10 of the 40 matrices, not 5, and the longest are 3,732,481 entries (neos-4332810-sesia), 194,469 (usafa), 141,121 (dlr2) and 62,516 (bab6). At the 0.5 to 0.6 microseconds per entry per thread of README_sweeps.md the sesia row costs 7.3 to 8.7 ms per fold, about the time of the whole best round Stage 0 measured on that matrix (8.37 ms, with chunks), and a row with 3.7 million columns is in the frontier of nearly every round. The host sums that row at about the same speed, so on this instance the device gains nothing on its largest row. On bab6 the 62,516-entry row adds about 0.13 ms to a round that Stage 0 measured at 0.35 ms. The design leaves this to a table in milestone 3 and to a choice between latency and new host hashes.
  FIX: Measure a third form next to the chunk kernel in milestone 3, which keeps the order of numerics.hpp and every host hash: compute the products a * bound, their errors, the infinite flags and the largest term for all entries of the row in parallel into scratch (many blocks), then let the 256 lane threads run only the two-sum chain over the precomputed pairs. The chain is the only part the order forces to be sequential; the gather of the column bounds, which dominates the per-entry latency, is not. That this cuts the latency by several times is inferred, not measured.

[serious] Several measurements the design promises cannot be made with the harness it describes: the thresholds of the first group from 'the logged propagation calls over the testbed', the host engine on 'frontiers between 10% and 100% of the rows' from the shadow log, and the condition 'no instance slower than host only by more than the larger of 5% and 2 ms' as a check on the device.
  WHY: The logged calls on which the device runs with engine automatic are the ones the selection admits; by the first defect that is no call on the 17 local instances and at most 25 calls on 11 instances for the rest, so the summed time the rule minimises has almost no terms, and to evaluate another threshold value the whole presolve has to be run again because the states diverge after the first device call. Frontiers of 10% to 100% of the rows after the first cascade occurred in the probe on three instances only (rd-rplusc-21 90%, radiationm18 85% and 55%, uccase9 29%), all on models below 5e5 nonzeros by then; elsewhere such frontiers exist only inside the first cascade, which the device does not take, so the table would be measured with first_cascade forced and would describe a regime the shipped rule never enters. The per-instance time rule cannot see the device: the eligible propagation work is well under a millisecond of host time on the instances I could measure, against run-to-run differences of up to 15.1% (Stage 0), so it can neither confirm a gain nor catch a loss of that size. Recording 'model, bounds, list at every propagation call' means 336 dumps for unitcal_7 and about 3 GB per dump for waipa. The shadow run itself is usable: host time on a copy was 0.97 to 1.88 times the time in place (minimum of 5, Mac).
  FIX: State for each table whether it is taken on calls the default rule admits or on forced calls, and take the forced tables with the configuration that would actually be shipped if they are to justify a default. Fix thresholds from per-call timers (device part against shadow), with a minimum number of calls and instances below which a threshold stays at 'host' by rule. Record states only for calls above a frontier size and cap the number per instance. Keep the per-instance time rule as a guard, and add a guard that can see the device: the summed per-call difference over each instance.

[minor] The baseline kernels of milestones 1 to 5 are lane groups for rows and columns up to 64 entries at every size, and the alternatives (one thread per column, the serial lane kernel for rows) arrive in milestones 3 and 6. The engine is only eligible from 5e5 nonzeros.
  WHY: Read from the names of the best compensated round per matrix in the stored Stage 0 files: lane groups are the fastest activity variant on 2 of the 9 matrices above 1e7 nonzeros (square47 and t11nonreg, where long rows dominate) and one thread per row up to 64 on 6; one thread per column up to 64 is the faster candidate scheduling on 12 of the 19 matrices from 1e6 nonzeros. So in most of the eligible range the first timings of milestone 2 and the tables of milestone 3 are taken with the slower column kernel. The row fallback of the design is not the kernel Stage 0 measured: Stage 0's one-thread kernel sums in storage order, the serial lane kernel must keep up to 32 lanes per side or walk the merge tree with a stack and adds a dd_add per lane, so there is no number yet for whether it wins anything above 1e7.
  FIX: Build one thread per column and the serial lane kernel in milestone 2, since neither can change a result, pick the scheduling per size class before any timing is quoted, and report the serial lane kernel against Stage 0's storage-order thread kernel so that the price of keeping one order is known.

[minor] The entries of a column are stored in the order of their CSR position in the class-ordered image, and a compaction of the image repeats all build steps including the stable radix transpose.
  WHY: The order inside a column then depends on the row classes, so any change of row lengths (a host rebuild that drops the entries of fixed columns, later clique extension) invalidates it and forces the sort. Stage 0 measured compaction of the old CSC at 0.70 times the radix transpose when entries are only deleted, and DESIGN.md 2.3 plans to use it; the layout gives that up. Nothing needs the CSR-position order: the candidate reduction is independent of order, csc_row already holds host row indices, and the search of write_row_values_kernel can run on host row index.
  FIX: Order the entries of a column by host row index. The uploaded host CSR is already in row order, so a stable sort by column on the kept slots before the rows are binned gives it at the same cost, and it survives re-binning of the rows. A compaction is then a stable select of the kept entries plus the re-binning of rows and columns, without a sort over the nonzeros.

[minor] Every round folds both activities of every frontier row, although the device never hands an activity to the host and a row with one finite side can only use one of them.
  WHY: From the Stage 0 matrix data, rows with exactly one finite side are a median of 83% of the rows per matrix and at least half of the rows on 27 of 40 matrices (computed as 2 * rows minus the two counts of finite sides, assuming no row without a finite side). On those rows half of the compensated arithmetic of the fold is unused, and Stage 0 prices compensated sums at 39% of the activity kernel.
  FIX: Fold only the sides whose row side passes side_usable, decided per row from row_side in the scan, and keep the two-sided fold for assertion builds, where it is compared with the host. Time it against the two-sided kernel before it replaces it.

[minor] The device fixed-cost budget is kept at 5 work units (50 ns) per input nonzero.
  WHY: From the stored node results the whole host presolve costs 59 to 348 ns per input nonzero on the instances from 5e5 nonzeros and propagation as a whole 0.1 to 33 ns per nonzero (waipa 0.1, kenana 15, motru 33). A budget of 50 ns per nonzero is 14% to 85% of the entire host presolve and more than all propagation work on every one of these instances, so it can never bind, and it is far above the design's own condition that no instance may be more than 5% slower, which corresponds to 3 to 17 ns, that is 0.3 to 1.7 units, per nonzero.
  FIX: Derive the budget from the time rule: a fixed share of the host engine's measured cost per nonzero, entered as a number of units per nonzero after the host cost per unit is measured, and show in the final table how much of it each instance used.
